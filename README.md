# 전남광주통합특별시 동구 가로등·보안등 점검 서비스

전남광주통합특별시 동구(2026-07-01 통합 전 광주광역시 동구)의 가로등·보안등 현장 점검, 고장 관리, 주민 신고를 처리하는 모바일 웹앱입니다.
직원 앱은 단일 HTML 파일(`index.html`)이며, Claude 아티팩트 공유 저장소·Firebase 공유 저장소·브라우저 체험 저장소를 지원합니다. 주민 신고 페이지는 `report/`에 따로 있습니다.

## 화면 구성

**스타일** — 글꼴은 Pretendard(동적 서브셋 CDN, 없으면 시스템 글꼴). 색은 밤하늘 남색 잉크와 나트륨등 주황을 기본으로, 상태색(정상 초록·점검필요 주황·고장 빨강·수리중 파랑)은 표찰·막대·칩·지도에서 같은 뜻으로 씁니다. 머리글은 한 줄 앱바(마크·이름·역할·연결 상태·화면 밝기 전환), 상태는 네 장의 카드 대신 비율 띠와 조치 필요 숫자 셋으로 보여 주고, 목록에서는 표찰 번호가 가장 큰 글자입니다. 화면 밝기 전환(자동·야간·주간)은 휴대폰 설정과 별개로 저장됩니다.

상세 화면(등 상세·점검, 표찰 스캔, 주변 찾기, 지도, 등 정보 수정, 순찰 결과 등)은 바텀시트가 아니라 **전체 페이지**로 열립니다. 위에는 뒤로가기(‹)와 제목이 고정되고, 등 상세에는 점검표·결과·이력·사진으로 바로 가는 칩이 함께 고정되며, 저장 버튼은 화면 아래에 붙어 있습니다. 휴대폰 뒤로가기로 닫힙니다. 넓은 화면(900px 이상)에서는 오른쪽 760px 패널로 열립니다.

| 탭 | 대상 | 주요 기능 |
|---|---|---|
| 현장 점검 | 점검자 | 고장·점검주기 경과 순 목록, 8항목 점검표, 등주 기울기 측정, 사진·메모, 점검 이력, 야간 차량 순찰 모드 |
| 관리 현황 | 담당 공무원 | 허브(상태 띠 + 조치 필요 등 + 관리 메뉴)에서 각 기능을 별도 페이지로 엽니다: 위치 분포, 종류별·법정동별 현황, 밝기 예측·보완 검토, 점검 결과 확인(검수·재점검 요청·CSV), 현장 등록, 미등록 관리, 표찰 없는 등, 야간 순찰 기록, 정보 수정된 등, 사용자·권한 |
| 주민 신고 | 주민 | **별도 페이지** `report/` (앱과 분리, 로그인 없음). 표찰 QR이 `report/?c=번호&lid=대장ID`를 열어 해당 등의 신고 양식이 뜸. 직원 앱의 주민 탭은 꺼 둠 |

## 역할과 권한

| 역할 | 볼 수 있는 탭 | 할 수 있는 일 |
|---|---|---|
| 관리자 | 전부 | 신고 처리, 미등록 등 대장반영·반려·삭제, 등 정보 수정·되돌리기, 도로망 다시 받기, 사용자·권한 관리 + 점검자가 하는 일 전부 |
| 점검자 | 현장 점검, 관리 현황(조회·현장 등록·순찰), 주민 신고 | 점검 결과 저장, 상태 변경, 야간 순찰, 현장 등록(미등록), 표찰 번호 기록, 밝기 검토, CSV |
| 주민(역할 없음) | 없음 | 안내 화면과 본인 사용자 ID만 표시. 주민 신고 기능을 켜면 신고 탭이 열림 |

- 역할은 `roles/{userId}`에 저장되며, 관리 현황의 "사용자·권한"에서 관리자가 지정합니다. 역할이 없는 사용자는 주민으로 취급됩니다.
- **처음 설정**: 관리자가 없으면 "내가 관리자 되기"로 초기 관리자를 지정합니다. Firebase는 `meta/setup`이 없는 동안 로그인한 사용자의 자기 관리자 등록을 허용하고, 설정 완료 뒤에는 관리자만 역할을 부여합니다. 아티팩트에서는 관리자가 지정되기 전 참여자에게 모든 기능이 열립니다. 소유자가 초기 설정을 마친 뒤 사용자를 초대하세요. 마지막 관리자 해제는 앱 화면에서 막습니다.
- 최근 신고·점검·순찰·등록을 한 사용자 중 역할이 없는 사람이 목록에 떠서 바로 점검자로 올릴 수 있고, 사용자 ID로 직접 추가할 수도 있습니다.
- **담당 행정동**: 사용자·권한에서 점검자마다 담당 행정동을 지정하면(roles.dongs) 그 점검자의 현장 점검 목록이 "내 담당 동"으로 좁혀지고(필터에서 끌 수 있음), 순찰 시작 시 담당 동이 기본 대상이 됩니다.
- **체험 모드**: 머리글의 "체험 역할"로 세 역할의 화면을 바꿔 볼 수 있습니다. GitHub Pages도 Firebase 설정 여부에 따라 체험 또는 공유 모드가 됩니다.
- **Firebase 권한**: 루트 `firestore.rules`를 실제 프로젝트에 배포해야 서버에서 역할을 강제합니다. 점검자는 상태·표찰·대표 사진·본인 좌표 제안을 기록하고, 좌표 원본·광원·철거·대장반영·검수는 관리자가 처리합니다. 점검·사진은 작성자를 확인하며, 점검자의 기존 증빙 내용 수정·삭제를 막고 동일 내용 재전송과 구버전 사진의 최초 점검 연결만 허용합니다. Google 로그인만으로 직원 권한을 얻지 않으며, 이메일 도메인 자동 제한은 구현되어 있지 않습니다.
- **아티팩트 한계**: 역할 구분은 화면에 적용되고 공유 DB는 참여자의 쓰기 가능 여부를 확인합니다. Firebase 규칙이 적용되는 환경이 아니므로 신뢰하는 사람에게 참여 권한을 부여해야 합니다.

## 현장 점검 사용성

- 점검표 8항목 중 일부만 체크하고 저장하면 "나머지를 양호로 기록할까요?"를 한 번 묻고 채워서 저장합니다. "모두 양호" 버튼도 있습니다.
- 작성 중이던 점검(체크·결과·메모·사진)은 상세 화면을 닫아도 같은 세션 안에서 등별로 복원되고, 목록에 "작성 중" 표시가 붙습니다. 저장 중 다른 등을 열어도 원래 점검 결과를 저장하며, 이후 수정한 내용과 새로 연 등의 초안은 지우지 않습니다. 새로고침·앱 완전 종료 뒤의 초안 복구는 지원하지 않습니다.
- **점검 저장**: Firebase는 사진·점검 이력·등 상태를 한 batch로 저장하고, 체험 모드는 한 번의 기기 저장으로 함께 반영합니다. 체험 저장 공간이 부족하면 저장 성공으로 표시하지 않고 기존 데이터와 초안을 유지합니다. 실패한 점검은 같은 세션에서 동일 ID·내용으로 재시도하며, 재시도 사이에 추가된 검수 정보도 보존합니다.
- **공유 저장의 범위**: 등 수정은 변경 필드만 보내므로 다른 단말의 관계없는 항목을 오래된 캐시로 덮어쓰지 않습니다. 아티팩트는 지원 API상 여러 문서를 순차 저장하여 중간 실패 시 일부 기록이 먼저 남을 수 있습니다. 같은 항목·변경 이력 배열의 동시 수정 충돌 해결, 앱 종료 후 실패 작업 복구, 순찰 등 다른 복수 문서 작업의 원자적 저장은 별도 개선 과제입니다.
- 버튼·칩은 최소 38~44px, 체크박스 20px로 장갑 낀 손에서도 누를 수 있게 했습니다.

## 동구 특화

- **행정동 13곳** (충장동·동명동·계림1·2동·산수1·2동·지산1·2동·서남동·학동·학운동·지원1·2동)을 기준으로 필터·동별 현황·보고서·순찰 범위를 집계합니다. 대장의 동은 법정동(31개)이라 `ADONG_OF`로 대응시키고, 동 선택 상자는 "행정동 전체 → 소속 법정동" 구조입니다.
- 계림·산수·지산은 법정동 하나가 1·2동으로 나뉘어 법정동만으로는 못 가르므로, 밝기 검토의 "도로망 불러오기"가 OSM 행정동 경계(admin boundary)도 함께 받아 등마다 행정동을 확정합니다(`ADONG_IDX`). 그 전에는 "계림동(1·2)"로 묶어 보여 줍니다. 구 경계는 지도에 점선으로 그립니다.
- 표찰 형식, 법정동 이름(충장로5가·금남로2가 등), 무등산국립공원 제외, 관리시스템(getPoint.json) 대장 구조 등은 동구 자료를 그대로 따릅니다.
- `ADONG_OF`의 법정동→행정동 대응 중 광산동·금동(충장동), 소태동·용산동(지원1동), 월남동(지원2동)은 공개 자료 기준이므로 구청 조직도와 다르면 그 표만 고치면 됩니다.

## 표찰 기반 식별

동구가 등주에 부착한 표찰을 관리번호로 사용합니다. 표찰은 두 종류이며, 보안등 표찰의 동 이름은 법정동(산수동, 지산동, 충장로5가, 금남로2가 …)입니다.

| 종류 | 표찰 | 번호 형식 | 예 |
|---|---|---|---|
| 가로등 | 초록 머리띠 "가로등", 왼쪽 파란 세로 띠 "관리번호" | 도로명 + 번호-가지번호 (옛 표찰은 숫자만) | `지호로 65-5`, `140-8` |
| 보안등 | 파란 "보안등 고장신고" | 행정동 + 번호 | `산수동 642`, `지산동 118` |

- **QR 스캔** — 새 라벨은 표시 번호(`c`)와 대장의 고유 ID(`lid`)를 함께 넣고, 유효한 ID를 먼저 사용해 같은 번호의 다른 등을 구분합니다. 주민 신고를 직원 앱으로 가져올 때도 ID로 연결하고 현재 대장 번호를 표시합니다. 명시된 ID가 삭제되었거나 대장에 없으면 다른 등으로 추정 연결하지 않고 미연결 신고로 보관합니다. 기존 번호만 있는 QR은 번호 파싱으로 처리합니다.
- **현장 화면 전환** — 스캐너·주변 찾기·순찰을 닫은 뒤 늦게 허용된 카메라 스트림은 즉시 종료하고, 이전 화면의 위치·방향 콜백을 새 화면에 반영하지 않습니다. 주변 찾기로 돌아오면 보정된 방향 안내를 다시 표시하며, 순찰을 끝내면 음성 인식과 화면 켜짐 유지도 해제합니다.
- **실시간 표찰 읽기** — QR이 없는 표찰도 카메라에 비추기만 하면 됩니다. 매 프레임 표찰 틀(파란·초록 테두리)을 찾아 화면에 네모로 표시하고, 틀이 0.7초쯤 멈추면 자동으로 고해상 프레임을 떠서 숫자를 읽습니다(휴대폰 안 Tesseract, 숫자 전용 엔진 약 1초). 읽은 번호를 대장과 맞춰 **현재 위치 기준 가까운 순**으로 후보를 띄우고, 근처에 그 번호가 하나뿐이면 바로 "이 등 점검하기"로 이어집니다. 번호가 없거나 비슷하면 반경 120m 안의 비슷한 번호를 함께 보여 줍니다. 밤·역광·바랜 표찰은 못 읽을 수 있으니 "자세히 읽기 · 직접 입력"으로 사진 경로(아래)로 넘어갑니다. 인식 엔진은 스캔 화면을 열 때 미리 받아 두고(처음 한 번 약 4MB) 서비스 워커가 캐시합니다. claude.ai 아티팩트에서는 CDN이 막혀 자동 읽기 대신 "표찰이 보여요 → 표찰 읽기" 버튼이 뜨고, 탭하면 AI가 읽습니다.
- **사진 인식** — 표찰 사진을 찍거나 올리면 틀을 찾아 잘라 QR → 숫자 → 동 이름 순으로 읽고(GitHub Pages·설치 앱은 기기 OCR, 아티팩트는 AI), 한전 전주번호(예: `9792C742`)도 함께 읽습니다. 틀을 못 찾으면 사진 위에 영역을 직접 그릴 수 있습니다.
- 읽은 번호가 대장에 없으면 "미등록"으로 표시하고 신규 등록 양식으로 이어집니다.

## 점검 결과 확인 (검수)

관리 현황 → "점검 결과 확인"에서 현장 점검 결과를 기간(7·30·90일·전체)·결과·점검자·미확인만으로 거르고, 점검표 양호 비율·불량 항목·메모·기울기·사진을 보며 검수합니다. 관리자가 **확인**을 누르면 `reviewedBy/reviewedAt`이 찍히고, **재점검 요청**을 누르면 사유가 기록되고 해당 등이 "점검필요 · 재점검 요청" 상태로 현장 점검 목록 위로 올라옵니다(새 점검을 저장하면 해제). 점검자별 건수와 불량 항목 상위도 같이 보입니다. 기본은 최근 40건, "지난 기록 더 불러오기"로 400건까지.

## 주민 신고 (분리)

주민은 직원 앱이 아니라 `report/index.html`을 씁니다. 표찰의 QR(관리 메뉴 → QR 라벨에서 인쇄)이 `report/?c=표찰번호&lid=대장ID`를 열고, 문제 유형·내용·사진 1장·현재 위치(선택)·연락처(선택, 보관 동의)를 받습니다. 번호를 직접 수정하면 QR의 기존 ID 연결을 해제합니다. 전달 방식과 실제 연락처는 `report/config.js`에서 설정합니다.

- **전달 수단 미설정**: 접수 버튼을 비활성화하고 "신고 접수 준비 중"으로 안내합니다. 예시 전화번호를 실제 연락처처럼 표시하지 않습니다. 현재 저장소의 `backend`, `sms`, `mail`은 미설정 상태입니다.
- **문자·이메일**: `sms` 또는 `mail`을 설정합니다. 페이지에서는 신고 내용만 준비하며, 사용자가 외부 앱에서 직접 보내야 합니다. 전송 전에는 접수 완료나 접수번호를 표시하지 않고, 사진은 외부 앱에서 직접 첨부하도록 안내합니다. 담당자가 직원 앱 **신고함**에 기록하고 상태를 관리합니다.
- **Firestore 직접 접수**: `backend:"firestore"`와 프로젝트 설정, 루트 `firestore.rules` 배포가 필요합니다. 서버 저장에 성공한 경우에만 접수 완료와 접수번호를 표시합니다. 공개 생성 요청은 허용 필드·길이·좌표·연락처 동의를 검사하고, 조회·수정·삭제는 역할이 지정된 직원에게만 허용합니다. 직원 앱의 **"QR 신고 가져오기"**로 신고함에 옮기고 원본에 가져오기 표시와 연락처·사진 삭제를 요청합니다. 신고함에서 완료 처리하면 연락처를 비웁니다.
- `privacyDays`는 보관 기간 안내값입니다. 해당 기간이 지나면 자동 삭제하는 예약 작업은 포함되어 있지 않습니다.
- 계획과 근거: `docs/citizen-report-plan.md`

직원 앱 **신고함**(관리 메뉴)은 전화·문자·이메일·방문·QR로 들어온 신고를 담당자가 기록하는 곳입니다. 등 번호를 넣으면 대장 등과 연결되어 등 상세에 "신고 N건"이 보이고, 접수→처리중→완료 상태와 CSV가 있습니다.

## 백업·이전

관리 현황 → 백업·이전(관리자). 현장 기록 전체(lights 덮어쓰기·inspections·reports·patrols·roles·photos 선택)를 JSON 한 파일로 내려받고, 같은 파일을 다른 백엔드(아티팩트 ↔ Firebase ↔ 체험)에 가져옵니다. 같은 ID는 건너뛰고 "덮어쓰기"를 켜면 교체합니다. 대장(`data/lights.json`)은 포함하지 않습니다.

## 보고서

관리 현황 → 보고서. 기간(이번 달·지난 달·최근 7/30일·직접 지정)과 동을 고르면 인쇄용 한 페이지가 만들어집니다: 표지(기간·작성자), 요약 숫자(대상 등·점검 건수·결과 분포·현재 조치 필요), 최근 6개월 월별 점검 추이(결과별 누적 막대), 법정동별 표, 점검자별 실적, 불량 항목 상위, 순찰·등록·수정 집계, 이상 발견 내역(최대 100건), 현재 조치 필요 등 목록(최대 150), 선택 시 사진 부록(원본 크기, 이상 건만/기간 내 전부, 작게·보통·크게, 같은 등의 "조치 전·후"는 나란히, 최대 48장). "인쇄 / PDF 저장", 동별·점검자별 "표 CSV", "요약 공유"(메신저용 텍스트)가 있습니다. 점검 기록은 최근 1,000건을 불러와 집계합니다.

화면·"요약 공유"·"표 CSV"는 같은 기간·동 선택으로 집계합니다. 선택 동의 등 수와 점검자 실적을 함께 좁히며, 전체 동을 대상으로 한 순찰은 해당 동의 통과·표시 등이 확인될 때 그 동 보고서에 포함합니다. 최근 기록 조회 상한은 그대로 적용되므로 기간 전체에 대한 무제한 집계는 아닙니다.

등 상세의 "이력서 인쇄"는 등 한 개의 대장 정보·점검 이력·정보 변경·순찰 통과·사진을 한 장으로 만듭니다(민원 회신·수리 지시서 첨부용).

## 점검 중 위치 확인

등 상세를 열면 "위치 확인" 상자가 휴대폰 GPS와 등록 좌표의 거리를 바로 보여 줍니다(최대 30초 동안 정확도가 좋아질 때까지 추적, "위치 다시 잡기"로 재시도). 25m 안이면 초록, 60m 안이면 주황, 그 밖이면 빨강으로 "다른 등이거나 좌표 오류일 수 있어요"라고 알립니다. "지도 보기"를 누르면 등록 좌표(주황)와 현재 위치(파랑, 오차 원)를 잇는 작은 지도가 뜹니다.

- 점검 결과를 저장하면 그때의 위치와 거리(`pos`, `posDist`)가 점검 기록에 남고, 이력·이력서에 "📍 위치 확인 12m" 또는 "등록 좌표에서 85m 떨어진 곳에서 점검"으로 표시됩니다.
- 거리가 벌어져 있을 때 **관리자**는 "현재 위치로 좌표 보정"으로 바로 좌표를 바꾸고(변경 이력에 남음), **점검자**는 "현재 위치를 좌표로 제안"만 할 수 있습니다. 제안(`posSuggest`)은 등 상세와 등 정보 수정 화면에 떠서 관리자가 "적용"(변경 이력에 "점검자 좌표 제안 적용") 또는 "지우기"합니다. 좌표가 없는 등은 같은 버튼으로 등록·제안합니다.

## 대표 사진

등마다 **대표 사진을 세 칸(전경·표찰·주변)** 둘 수 있습니다. 등주 전체, 표찰, 주변 길이 각각 보이게 한 장씩 찍어 두면 현장에서 "이 등이 맞나"를 바로 확인할 수 있습니다.

- 등 상세와 등 정보 수정 화면 위쪽의 "대표 사진" 상자에 칸이 셋 있고, 칸마다 📷(찍기)·🖼(앨범)·×(빼기)로 넣고 바꿉니다(점검자 이상). 사진 이력의 크게 보기에서 "대표 사진으로"를 누르면 전경·표찰·주변 중 어느 칸에 넣을지 고를 수 있고(이미 있으면 "바꾸기"), 빼기는 대표 지정만 풀고 사진 이력은 남깁니다.
- 비어 있는 전경·표찰 칸은 점검 결과를 저장할 때 **같은 구분의 점검 사진이 자동으로 채웁니다**(저장 토스트에 표시). 고장 부위·조치 전후 사진은 자동으로 쓰지 않습니다.
- 저장: 원본(긴 변 1000px)은 `photos/{auto}`(kind `rep`, label = 칸 이름)에, 등 기록(`lights/{id}`)에는 `reps:{전경:{id,at,by},…}`와 **첫 칸(전경→표찰→주변 순) 한 장의 112px 썸네일 `photoT`**(3~5KB)만 둡니다. 목록 행·지도 팝업·순찰 카드가 이 썸네일을 추가 읽기 없이 보여 주고, 등 상세·이력서는 세 장을 사진 이력과 함께 불러옵니다. 5,500등 전부 채워도 대장 스냅샷은 20MB대입니다.
- 표찰 스캔에서 "현재 위치로 바로 저장"한 미등록 등의 표찰 사진(`photo`)은 표찰 칸으로 취급합니다.
- **"이 등이 맞나요?"** — 주변 찾기 목록, AR 목록·안내 카드("사진 확인"), 야간 순찰 카드, 표찰 스캔 후보에서 썸네일을 누르면 화면 아래에 그 등의 대표 사진 세 장이 가로로 떠서, 앞에 보이는 등주·배경과 견주어 볼 수 있습니다(AR·순찰에서는 카메라 화면이 위에 그대로 남음). "맞아요"는 점검(또는 순찰 선택·스캔 확정)으로 이어지고, "아니에요 · 다음 후보"는 근처 다른 등의 사진으로 넘어갑니다. 사진이 쌓인 뒤 자동 비교(이미지 임베딩 또는 LLM 비전)를 올릴 수 있는 자리입니다.

## 점검 사진

점검 결과 저장 화면에서 사진을 최대 6장 붙입니다. 사진을 고르면 바로 편집 화면이 떠서 구분(전경·표찰·고장 부위·조치 전·조치 후·기타)을 고르고, 빨간 펜으로 고장 부위를 표시하고, 설명을 적습니다. 저장 시 사진 아래에 "표찰번호 · 일시 · 점검자 · 좌표 · 구분" 캡션이 새겨져(끌 수 있음) 보고서 증빙으로 그대로 쓸 수 있습니다.

- 사진은 긴 변 1000px JPEG(60~140KB)로 줄여 `photos/{auto}`에 한 장씩 저장하고, 점검 기록에는 180px 썸네일만 둡니다. 체험 모드에서는 localStorage 용량(약 5MB) 때문에 수십 장이 한계입니다.
- 등 상세의 **사진 이력**에 그 등의 사진이 시간순으로 모이고, 눌러서 크게 보기·이전/다음·내려받기, "조치 전"과 "조치 후"가 모두 있으면 **전·후 비교**, **사진 대지(인쇄/PDF)** 를 만들 수 있습니다.

## 야간 차량 순찰

차로 돌며 꺼진 등을 찾는 야간 순찰용 화면입니다(현장 점검 탭 → 야간 순찰). 동승자가 조작하는 것을 전제로 합니다.

- GPS 진행 방향 기준으로 앞쪽 140m·좌우 30m 안의 등이 가까운 순으로 큰 카드로 뜨고, 좌/우/정면과 거리를 표시합니다. 시속 40km에서 2초에 하나씩 지나가므로 버튼은 두 개뿐입니다: **꺼짐(고장)**, **어둡거나 깜빡임(점검필요)**. 기본으로 맨 위 등에 적용되고, 카드를 먼저 누르면 그 등에 적용됩니다. 마지막 표시 취소, 진동·음성 안내(조치 필요 상태인 등 접근 시), 화면 꺼짐 방지(Wake Lock), 일시정지를 지원합니다.
- 차가 25m 안으로 지나간 등은 자동으로 "지나간 등"에 들어가고, 표시하지 않은 등은 저장 시 **점등 확인**으로 남습니다(점검주기는 갱신하지 않음).
- **대상 동과 진행률** — 순찰 화면에서 동을 고르면 그 동의 등 중 몇 %를 지나갔는지 진행 막대로 보입니다. 관리 현황 "야간 순찰 기록"의 최근 30일 순찰 범위(동별 %)에서 가장 낮은 동부터 바로 순찰을 시작할 수 있고, "순찰 안 된 등 지도"로 공백을 봅니다.
- **켜져 있음(정상)** — 앞 등이 고장·점검필요·수리중 상태면 초록 버튼이 떠서 수리 완료를 현장에서 바로 확인·정상 처리합니다.
- **여기 어두움** — 등이 없는 어두운 지점을 GPS로 찍습니다(가장 가까운 등과 거리 표시). 요약에서 미등록 등록 양식으로 넘길 수 있고, 경로 지도에 보라 점으로 남습니다.
- **음성 명령**(안드로이드 Chrome) — "꺼짐/고장", "깜빡임/어두움", "켜져 있음/정상", "취소", "여기"를 말해서 손을 떼고 기록합니다. 음성 안내(읽어주기)와 별개입니다.
- **전체 화면** — 순찰은 바텀시트가 아니라 전체 화면으로 열리고 스크롤 없이 한 화면에 맞춥니다(위: 대상 동·진행률·끝, 가운데: 카메라/지도 + 번호 카드, 아래: 버튼과 보기 전환). 가로 모드에서는 왼쪽 카메라/지도, 오른쪽 카드·버튼. 휴대폰 뒤로가기는 순찰을 끝내고 요약으로 갑니다(기록 유지).
- **하나의 순서, 세 가지 보기** — 앞 등 목록(①②③④)이 기준이고, 카메라와 지도는 같은 번호를 같은 등에 붙여 보여 줍니다. 어느 화면에서 눌러도 같은 등이 선택되고(주황), 버튼은 그 등에 적용됩니다. 보기는 "목록만 / 카메라 / 지도" 중 하나만 켜집니다.
- **지도 보기** — 순찰 화면 안에 차 위치(진행 방향 화살표)·이동 경로·주변 등(상태 색)·점등 확인(초록 점)·표시한 등·어두운 지점이 실시간으로 그려지는 지도. 기본은 차를 따라가고, 지도를 끌면 멈췄다가 "따라가기"로 복귀. 지도의 등을 누르면 선택돼 버튼이 그 등에 적용됩니다.
- **카메라 보기** — 순찰 화면 위에 후면 카메라를 띄우고, GPS 진행 방향 기준으로 앞 140m·시야각 안의 등을 번호·거리 마커로 겹쳐 보여 줍니다(차 안에서는 나침반이 흔들리므로 나침반 대신 주행 방향을 씁니다). 마커를 누르면 그 등이 선택돼 버튼이 그 등에 적용됩니다. 카드 목록에도 진행 방향 기준 화살표가 붙습니다.
- GPS 정확도 표시(25m 넘으면 주황), 앱이 백그라운드에서 돌아오면 GPS·화면 켜짐을 다시 잡습니다.
- 끝내면 요약(거리·시간·지나간 등·표시·어두운 지점)과 표시한 등 목록을 확인하고 저장합니다. "일지 공유"로 텍스트 일지를 메신저에 보낼 수 있고, 관리 현황에서 순찰 일지 CSV를 내려받습니다. 표시한 등은 `inspections`에 `patrol:true` 기록이 생기고 상태가 바뀝니다. 순찰 자체는 `roles/{userId}
  role(admin|inspector|resident), name, at, by

patrols/{auto}`에 경로·지나간 등·표시 목록으로 저장되어 관리 현황 "야간 순찰 기록"에서 경로 지도로 볼 수 있고, 등 상세에 "순찰 통과 날짜"가 표시됩니다.

## 등 정보 수정

등 상세 화면의 "등 정보 수정"(관리자 권한)에서 광원·등주·점멸기·전주번호·교체 연도·좌표·철거 여부·비고를 고칩니다. 좌표는 현재 위치로 바꾸거나 지도의 핀을 끌어 옮깁니다. 대장 원본(`data/lights.json`)은 바뀌지 않고 `lights/{id}`에 바뀐 값과 변경 이력(`edits`: 시각·수정자·항목별 이전값/변경값)이 쌓이며, 마지막 변경은 되돌릴 수 있습니다. 관리 현황의 "정보 수정된 등"에서 모아 보고 CSV로 내보내 도로조명 관리시스템 대장에 반영합니다.

## 밝기 예측·보완 검토

실측 조도가 없으므로 모델로 추정합니다. 대장에서 종류별 이웃 간격 분포를 구해(중앙값 약 20m) 상위 10% 간격을 검토 기준으로 삼고, 광원 종류(LED·CDM·나트륨·삼파장)와 상태(고장·수리중은 꺼짐)로 각 등의 유효 반경을 보정합니다. 기준값은 `LIGHT_MODEL`에 있습니다. 검토 방식은 두 가지입니다.

- **도로 따라 검토** — OpenStreetMap 도로 중심선(간선·주택가·생활도로·진입로·보행로)을 8m 간격으로 걸으며 합산 밝기가 약한 구간을 찾습니다. 고장·수리중 등의 영향을 받는 구간, 근처에 등이 전혀 없는 구간, 길이, 도로 등급 순으로 정렬하고 지도에 굵은 선으로 표시합니다. 공원·건물 너머의 등은 계산에 들어가지 않습니다.
  - 제외 대상: 아파트 단지·학교·대학·병원 부지 안(`landuse=residential`+`residential=apartments`, `amenity=school|university|college|hospital`), 숲·산·묘지·국립공원(`natural=wood|scrub`, `landuse=forest|cemetery`, `boundary=national_park`), 주차장 통로·사유지 진입로(`service=parking_aisle|driveway`, `access=private`). 이런 곳은 관리 주체가 다르거나 조명 대상이 아니므로 후보에서 뺍니다.
  - 90m 안에 등록된 등이 하나도 없는 구간(아파트 관리등·산길·농로일 가능성)은 기본으로 숨기고, 체크박스로 볼 수 있습니다.
- **등 간격으로 검토** — 도로망이 없을 때의 대체 방식. 이웃한 두 등의 간격이 기준을 넘거나 중간 지점이 약한 쌍을 후보로 뽑습니다. 도로 형상을 모르므로 공원·건물 너머의 쌍도 섞입니다.

두 방식 모두 보완 지점 좌표를 현장 등록 양식으로 넘기거나 CSV로 내보낼 수 있습니다. 현장 확인 순서를 정하는 용도입니다.

**도로망** — "도로망 불러오기"를 누르면 보는 사람의 브라우저가 Overpass API에서 동구 범위(`ROAD_BBOX`)의 도로와 단지·숲 영역을 한 번 받아(약 4MB) IndexedDB에 저장하고, 공유 데이터베이스가 있으면 `patrols/{auto}
  start, end, dist(m), by, dong, passed[lightId…], marks[{id, code, result(고장|점검필요|정상), at}],
  spots[{lat, lng, acc, at, near, nearD}], track[[lat,lng]…]

roads/part-N`(190KB 단위)과 `roads/meta`로 올려 다른 휴대폰은 다시 받지 않게 합니다. 도로 데이터 © OpenStreetMap contributors (ODbL).

## 데이터 구조

**대장(`data/lights.json`)** — 도로조명 관리시스템(getPoint.json)에서 변환한 동구 전체 등 5,553개. 컬럼형 JSON(`cols` + `rows`)으로 페이지와 함께 배포되며, 앱은 시작 시 이 파일을 읽습니다.

대장이 바뀌면 관리시스템에서 getPoint.json을 받아 변환합니다: `node scripts/build-registry.mjs getPoint.json data/lights.json`. 표찰 번호 해석(법정동 접두·가로등 도로명/번호·철거·표찰없음), 7자리 좌표 반올림, 동 이름 없는 등의 동 추정(가장 가까운 등)이 스크립트에 들어 있습니다.

```
cols: id, lampId, label, code, kind(가로등|보안등|공원등|특이등), dong(법정동), num, road, main, sub,
      lat, lng, lampType, pole(등주), sw(점멸기), removed(철거), noPlate(표찰없음), dongGuess(동 추정)
```

**현장 기록(공유 데이터베이스)** — 대장은 그대로 두고 바뀌는 값만 저장합니다. 체험 모드에서는 같은 구조를 브라우저 localStorage에 둡니다.

```
lights/{id}        대장 id와 같은 키. status(정상|점검필요|고장|수리중), lastInspected, lastResult, updatedAt
                   표찰을 새로 단 경우: code, num/road/main/sub, plateFixed, plateFixedAt
                   정보 수정: lampType, pole, sw, poleNo, replacedYear, lat, lng, removed, removedAt, note,
                   edits[{at, by, changes[{f, from, to}], undone}] (최근 30건)
                   현장에서 발견한 미등록 등(id np-… / bd-… / gl-…): 전체 필드 + reg(미등록|대장반영|반려),
                   noPlate, lat, lng, acc, photo, note, foundAt, foundBy, linkedId(기존 등과 연결 시)

inspections/{auto}
  lightId, code, dong, date, checks{}, faults[], result, memo, tiltDeg, inspector,
  photoN, thumbs[{id(photos 문서), label, t(썸네일)}], patrol(순찰 기록이면 true)   (photo: 옛 단일 사진)
  reviewedBy, reviewedAt(검수), redo, redoNote, redoBy, redoAt(재점검 요청)

photos/{auto}
  lightId, code, dong, inspId, label, note, data(JPEG dataURL), w, h, at, by, kind

reports/{auto}
  issue, location, dong, code, lightId, desc, photo, status(접수|처리중|완료),
  createdAt, updatedAt, reporterId

roads/part-N          OpenStreetMap 조각 { ways:[{id,name,type,sv,priv,pts:[[lat,lng],…]}], areas:[{t(apt|forest),name,pts}] }
roads/meta            ver(ROADS_VER), at, parts, count, areas, attribution — ver가 다르면 다시 받음
```

## 앱으로 설치 (PWA)

GitHub Pages 주소를 열면 Android Chrome은 "앱으로 설치" 띠가, iPhone은 "공유 → 홈 화면에 추가" 안내가 뜹니다. 설치하면 전체 화면으로 열리고 홈 아이콘 길게 누르기에 "표찰 스캔"·"야간 순찰" 바로가기가 있습니다.

- `manifest.webmanifest` — 이름·아이콘(`icons/`)·테마색·바로가기
- `sw.js` — 앱 셸·대장·기본 라이브러리·아이콘을 설치 시 캐시합니다. HTML·JavaScript·설정·manifest는 최대 3초 동안 네트워크를 먼저 확인하고 실패 시 캐시를 사용합니다. 대장·이미지는 캐시를 먼저 표시하면서 갱신합니다.
- 지도 타일(최대 600장)과 사용한 OCR·글꼴·Firebase SDK 파일을 캐시합니다. Firebase SDK를 포함해 처음 필요한 파일과 로그인·자료 받기는 온라인에서 완료해야 합니다. `VERSION`을 바꾸면 이전 앱 캐시를 정리합니다. 아티팩트에서는 서비스 워커를 등록하지 않습니다.
- Firebase는 저장된 로그인 상태와 읽기 캐시가 있으면 오프라인에서도 시작하고, 프로필 갱신의 서버 응답을 기다리지 않고 캐시 구독을 시작합니다. SDK의 쓰기 큐는 재연결 시 전송하며, 서버 확인 전 점검 저장은 대기 상태일 수 있습니다. 체험 모드는 계속 기기에 저장하고, 아티팩트 공유 저장은 연결이 필요합니다.

## Firebase 적용 (독립 운영)

`firebase-config.js`에 프로젝트 값을 넣으면 GitHub Pages에서 열어도 체험 모드가 아니라 **공유 저장소 모드**로 동작합니다. 아티팩트(claude.ai) 안에서는 무시되고 기존 아티팩트 DB를 씁니다.

- 로그인: Google 계정. 로그인 전에는 로그인 화면이 표시되고, 직원 데이터 접근은 관리자가 부여한 역할과 서버 규칙으로 제한합니다.
- 저장소: Firestore, 컬렉션 구조는 아티팩트 DB와 같습니다(lights·inspections·reports·patrols·roles·photos·roads + users·meta). 오프라인에서 저장하면 SDK가 큐에 두었다가 연결되면 올립니다(앱바에 "오프라인" 표시).
- 역할 강제: 루트 `firestore.rules`가 `roles/{uid}`와 작업별 허용 필드를 확인합니다. 역할이 없는 계정은 직원 업무 기록을 읽거나 쓸 수 없습니다. 본인 프로필 쓰기와 초기 관리자 설정은 별도 규칙을 따릅니다.
- 주민 신고(`citizen_reports`)도 같은 규칙 파일에 있습니다.
- 현재 `firebase-config.js`는 `null`입니다. Firebase를 설정한 뒤 연결·초기화에 실패하면 연결 오류와 재시도 화면을 보여 주며 체험 저장소로 자동 전환하지 않습니다.
- **Pages 배포와 Firestore 규칙 배포는 별개입니다.** GitHub에 규칙 파일을 커밋하거나 Pages를 배포해도 실제 Firebase 프로젝트의 규칙은 바뀌지 않습니다. Firebase 콘솔에서 게시하거나 올바른 프로젝트를 지정한 Firebase CLI 배포가 필요합니다.

설정 순서(관리자):

1. console.firebase.google.com → 프로젝트 만들기 → **Firestore 데이터베이스** 만들기(프로덕션 모드, asia-northeast3)
2. Firestore → 규칙 탭에 저장소의 `firestore.rules` 전체를 붙여넣고 게시
3. **Authentication** → 로그인 방법 → Google 사용 → 승인된 도메인에 `lanian.github.io` 추가
4. 프로젝트 설정 → 내 앱 → 웹 앱 추가 → `apiKey`, `authDomain`, `projectId`를 `firebase-config.js`에 넣기(주석의 예 참고). 주민 신고 자동 접수를 쓰려면 `report/config.js`에도 같은 `apiKey`·`projectId`와 `backend:"firestore"`
5. 커밋·푸시 → Pages 주소를 열어 Google 로그인 → 관리 현황 "내가 관리자 되기" → 사용자·권한에서 점검자 지정
6. (선택) 기존 기록은 **백업·이전**에서 JSON으로 내보내고 새 저장소에서 가져옵니다. 사용자 ID는 백엔드마다 다를 수 있으므로 역할은 새 계정의 ID에 맞게 다시 지정합니다.

## 실행 환경에 대한 안내

`index.html`은 세 가지 모드로 동작합니다: ① Claude 아티팩트(`window.claude.use`) ② Firebase(`firebase-config.js` 설정 시) ③ 체험 모드(둘 다 없을 때, 이 기기에만 저장). 모드는 `boot()`에서 정해집니다.

기본 설정의 Pages는 이 기기에만 저장하는 체험 모드입니다. 공유 운영은 아티팩트에서 실행하거나 Firebase 프로젝트·직원 역할·보안 규칙을 준비한 뒤 사용합니다. 설정 파일과 규칙을 수정했다는 사실만으로 운영 연결이나 실제 규칙 배포가 완료되지는 않습니다.

## 변경 검증과 배포

앱 검사는 Node.js 24에서 실행하며 별도 패키지 설치가 필요 없습니다. JavaScript 문법, PWA 아이콘·manifest, 대장 ID·좌표·행 수, 저장·보고서·신고·현장 기능의 회귀검사를 확인합니다.

```bash
node scripts/check.mjs
```

Firestore 규칙은 로컬 에뮬레이터에서 별도로 확인합니다. Node.js 24, Java 21, npm이 필요하며, 아래는 Bash에서 저장소 루트를 기준으로 실행하는 예입니다. 도구 버전은 `.github/workflows/checks.yml`과 맞춥니다.

```bash
DG_TOOLS_DIR="$(mktemp -d)"
npm install --prefix "$DG_TOOLS_DIR" --no-audit --no-fund --ignore-scripts \
  firebase-tools@15.34.1 @firebase/rules-unit-testing@3.0.3 firebase@10.12.2
NODE_PATH="$DG_TOOLS_DIR/node_modules" \
  "$DG_TOOLS_DIR/node_modules/.bin/firebase" emulators:exec \
  --only firestore --project demo-donggu-streetlight \
  "node --test scripts/tests/firestore-rules.emulator.cjs"
```

`firebase.json`의 로컬 Firestore 포트는 `8089`입니다. 테스트는 `demo-donggu-streetlight`와 로컬 에뮬레이터만 사용하며 운영 데이터베이스에 접속하지 않습니다. 점검자의 허용 작업과 관리자 전용 작업, 증빙 불변성·작성자, 주민 신고의 입력·열람 권한을 검사합니다. 에뮬레이터 연결 없이 해당 테스트 파일만 실행하면 검사가 건너뛰어지므로 위 명령을 사용합니다.

PR과 GitHub Pages 배포 전에 앱 검사와 규칙 검사를 실행하고, 모두 성공해야 Pages 배포를 진행합니다. Pages에는 실행에 필요한 정적 파일만 올립니다. 이 과정은 실제 Firebase 규칙을 배포하지 않습니다. 카메라·GPS·나침반·오프라인 복귀의 실제 휴대폰 동작은 현장 확인이 필요합니다.
