# 전남광주통합특별시 동구 가로등·보안등 점검 서비스

동구의 가로등·보안등 현장 점검, 야간 순찰, 주민 신고, 보수 작업과 자재 관리를 위한 모바일 웹앱입니다. 직원 화면은 `index.html`과 `app/` 모듈, 주민 신고 화면은 `report/`로 구성됩니다.

**기본 설정은 이 기기에만 저장하는 체험 모드입니다.** Firebase 프로젝트·직원 계정·App Check·Functions·예약 작업의 실제 운영 설정과 배포는 별도로 해야 합니다. 저장소에 코드가 있다는 사실이나 GitHub Pages 배포만으로 공유 운영과 주민 접수가 시작되지는 않습니다.

## 시작하기

1. 배포된 페이지를 열거나, 로컬에서 아래 명령으로 실행해 `http://localhost:8080`을 엽니다.
2. 현장 점검에서 시설을 선택해 점검표·사진·결과를 기록합니다. 관리 현황에서 보수 작업, 저장 대기함, 업무 현황을 확인할 수 있습니다.
3. 여러 직원이 함께 쓰려면 [배포 안내](deploy/README.md)에 따라 Firebase와 역할을 설정합니다. 최초 관리자는 운영자가 확인한 UID를 서버 설정 도구로 지정합니다.

```bash
python3 -m http.server 8080 --bind 127.0.0.1
```

로컬 서버 명령은 개발 확인용입니다. 공개 서버에는 [공개 파일 목록](deploy/README.md#공개할-파일)만 배포합니다.

## 주요 화면

| 화면 | 하는 일 |
|---|---|
| 현장 점검 | QR·표찰 OCR, 주변 시설 찾기, 8항목 점검표, 사진 최대 6장, 기울기·위치 확인, 이력 조회 |
| 야간 순찰 | GPS 경로·근접 통과, 직접 확인한 켜짐·꺼짐·깜빡임, 어두운 지점 기록 |
| 보수 작업 | 담당자·기한·우선순위 배정, 조치 전후 사진, 사용 자재·실측 조도, 완료 검수·재작업 |
| 미점검·방문 계획 | 기본 90일의 점검 주기, 기록 없음·기한 초과·재점검 구분, 최대 200개 시설의 방문 순서 |
| 저장 대기함·초안 | 작성 내용 복구, 미전송 작업·실패·충돌 확인과 재시도 |
| 관리 현황 | 점검 검수, 기간 보고서·CSV, 업무 현황, 대장 갱신 비교, 자재·재고, 백업·복원, 권한·감사 |
| 주민 신고 | 로그인 없는 별도 `report/` 페이지. QR의 시설 ID 연결, 서버 접수 또는 설정된 문자·이메일 안내 |

행정동 필터와 법정동 대장 정보를 함께 사용합니다. 동별 경계는 지도 자료가 준비된 범위에서 구분합니다. 방문 순서는 **직선 거리 기준**이며 차량 통행 경로 안내가 아닙니다. 밝기 예측은 상대 모델 값이고 조도계 실측·적합 판정과 구분합니다.

## 저장 방식과 복구 범위

| 환경 | 저장·복구 | 업무 지원 범위 |
|---|---|---|
| 체험 모드 | 업무 기록과 초안·대기 작업을 이 브라우저의 IndexedDB에 보관. 이전 localStorage 기록은 이관 | 한 기기에서 점검·순찰·보수·재고·대장 갱신 체험. 다른 기기와 자동 공유하지 않음 |
| Firebase 공유 PC — 기본값 | 로그인은 세션, 초안·대기함은 현재 창의 메모리. Firestore 영속 캐시를 켜지 않음 | 공유 업무 가능. 새로고침·창 종료 전에 초안과 미전송 항목을 처리 |
| Firebase 현장 전용 기기 — 사용자가 선택 | 계정·프로젝트별 초안과 대기 작업, Firestore 캐시를 기기에 보관 | 다시 열어 복구 가능. 서버 작업은 연결 후 완료 여부 확인 |
| Claude 아티팩트 | 참여자의 공유 DB 사용. 기기 보관이 가능하면 초안·대기 작업 복구 | 기본 점검·순찰 지원. 원자적 조건부 저장이 필요한 보수·재고·대장 갱신은 Firebase 또는 체험 모드 사용 |

기기 보관을 사용할 수 없으면 초안 저장 방식을 화면에 안내합니다. 브라우저 데이터 삭제·저장 공간 회수·기기 교체 뒤의 복구를 보장하지 않으므로, 완료된 기록은 별도로 백업합니다. Firebase 설정 후 초기화가 실패해도 체험 저장소로 자동 전환하지 않습니다.

저장 대기 작업은 고정 ID와 내용 확인값으로 재시도합니다. 새 화면이나 이후 수정한 초안을 이전 작업의 완료로 지우지 않습니다. 같은 문서가 다른 직원에게 변경된 경우에는 충돌을 표시하므로 최신 내용을 확인해야 합니다. 자세한 절차는 [업무 운영 안내](docs/operations-guide.md)를 참고하세요.

## 권한과 주민 접수

- **관리자**: 직원 역할·보수 배정·검수·대장·재고·신고 처리·복원 관리.
- **점검자**: 현장 점검·순찰·미등록 시설·표찰·대표 사진·좌표 제안, 본인에게 배정된 작업의 시작과 완료 요청.
- **역할 없는 로그인 사용자**: 직원 접근 신청. Google 로그인만으로 직원 자료 접근 권한이 생기지 않습니다.
- Firebase 권한은 실제 프로젝트에 배포한 `firestore.rules`가 강제합니다. 아티팩트·체험의 역할 선택은 서버 인증을 대신하지 않습니다. 담당 동은 화면 필터이며 시설 자료의 서버 접근 경계를 동별로 나누지는 않습니다.

주민 자동 접수는 `backend: "gateway"`와 App Check를 연결합니다. 공개 Firestore 직접 생성은 차단되어 있습니다. 전달 수단이 없으면 준비 중으로 표시하며 접수 완료를 표시하지 않습니다. 문자·이메일은 사용자가 외부 앱에서 직접 보내고, 서버 접수번호는 게이트웨이 저장 성공 뒤에만 표시합니다.

[주민 신고 운영 안내](docs/citizen-report-plan.md)와 [서버 보안·보관 안내](docs/security-operations.md)에 설정과 개인정보 처리 범위를 정리했습니다.

## 데이터와 집계

배포 대장 `data/lights.json`은 `cols`·`rows`·`count` 형식입니다. 시설 ID를 점검·사진·신고·보수 기록의 연결 키로 사용합니다. QR에는 표시 번호 `c`와 시설 ID `lid`를 함께 넣습니다. 명시된 ID가 없어진 경우 다른 시설로 추정 연결하지 않습니다.

| 저장 항목 | 용도 |
|---|---|
| `lights`, `lightFields` | 대장 위의 현장 변경. 아티팩트는 불변 변경 로그를 합쳐 읽음 |
| `inspections`, `photos`, `patrols` | 점검·원본 사진·순찰. 고정 작업 ID로 재시도 |
| `reports`, `citizen_reports` | 직원 신고함과 서버 주민 접수 원본 |
| `workOrders`, `workEvents` | 현재 보수 상태와 변경 불가 처리 이력. 검수 비용은 `accountedCost`·이벤트 `costDelta`로 관리 |
| `inventory`, `inventoryMoves` | 현재 자재 수량과 입출고 이력 |
| `roles`, `users`, `joinRequests`, `settings` | 역할·사용자·직원 신청·업무 기준 |
| `auditEvents` | Functions가 기록하는 서버 감사 이력. Firebase 클라이언트의 수정·복원 대상에서 제외 |
| `roads` | 다시 받을 수 있는 도로·경계 캐시 |

대표 사진은 `repWide`·`repPlate`·`repAround`의 독립 슬롯에 `{id, at, by, thumb}`를 저장하고 `null`로 지정을 해제합니다. 구형 `reps`·`photoT`·`photo`는 읽기 호환합니다. 사진 원본은 `photos`에 남습니다.

점검 이력은 처음에 최근 40건을 표시하고 전체 기록을 추가 조회할 수 있습니다. 보고서·백업·CSV는 고정 400/1,000/20,000건으로 잘라 내지 않고 필요한 자료를 끝까지 읽습니다. Firebase의 완전한 보고서·백업에는 서버 연결이 필요합니다. 업무 현황의 오프라인 캐시 조회는 화면에 별도로 표시합니다. 아티팩트 API가 알리지 않고 결과를 제한하는 경우 클라이언트만으로 완전성을 증명할 수 없습니다.

업무 현황의 검수 횟수는 `workEvents`를 기준으로 하므로 재배정해도 과거 실적이 유지됩니다. 기간 자재비는 검수 이벤트의 비용 증감 합계입니다. 미완료·기한 초과·미처리 신고는 현재 상태를 보여 줍니다.

대장 변환은 다음 명령을 사용합니다. 현장 변경과 비교해 적용하려면 관리 메뉴의 **대장 갱신 비교**를 사용합니다.

```bash
node scripts/build-registry.mjs getPoint.json data/lights.json
```

## 설치·오프라인·업데이트

Android·iOS의 브라우저 설치 기능으로 홈 화면에 추가할 수 있습니다. 앱 셸과 대장은 서비스 워커가 보관합니다. 사용자가 새 버전 적용을 선택할 때 초안·미전송 작업을 확인하며, 다른 탭의 업데이트로 작성 중인 화면을 자동 새로고침하지 않습니다.

처음 필요한 파일·로그인·업무 자료·OCR 엔진과 언어 파일은 온라인에서 준비해야 합니다. 기본 OSM 타일은 서비스 워커가 가로채거나 지역 단위로 내려받지 않습니다. 허가된 별도 제공기관을 설정한 경우에만 지정한 보관 정책을 적용합니다. [현장·PWA 검증 안내](docs/field-validation.md)에 센서와 실제 장비 확인 범위를 설명했습니다.

## 검사와 배포

Node.js 24에서 앱 검사에는 별도 패키지 설치가 필요 없습니다.

```bash
node scripts/check.mjs
```

서버 단위 검사는 별도 의존성을 설치합니다. 배포되는 Functions 런타임은 Node.js 22입니다.

```bash
npm ci --prefix functions --include=optional --ignore-scripts --no-audit --no-fund
npm test --prefix functions
```

앱·서버·규칙·브라우저 검사 명령과 공개 파일 목록은 [배포 안내](deploy/README.md)에 있습니다. CI는 검사가 성공한 뒤 Pages에 공개 앱 파일만 게시합니다. **Pages 배포와 Firebase 규칙·인덱스·Functions·예약 작업의 운영 반영은 별개입니다.** 실제 카메라·GPS·나침반·OCR·장시간 오프라인 동작은 현장 장비에서 확인해야 합니다.
