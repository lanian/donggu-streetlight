# 필수 유지보수 기능 구현 · v61

`v61-maintenance`는 유사한 시설 관리 앱에서 필요한 기능으로 검토한 여덟 항목을 반영한 로컬 개발 버전이다. 이전 v60은 배포됐으며, 이번 구현은 아직 커밋·푸시·실배포하지 않았다. Firebase 프로젝트와 주민 접수 설정은 유지했다.

위 내용과 아래 검사 수는 최초 v61 로컬 구현 당시의 기록이다. 공개 v72 위에 통합한 v73 후보와 최신 수정·검증·서버 연결 조건은 [2026-11-12 후보 검증](implementation-maintenance-release-2026-11-12.md)을 참고한다.

## 추가한 업무 흐름

| 기능 | 사용하는 곳과 동작 |
|---|---|
| 배정 확인·긴급 알림함 | 보수 작업에서 미확인 배정, 긴급, 기한 임박·초과, 보류 확인일을 조회한다. 현재 담당자가 배정 확인을 남기며 재배정하면 확인 상태가 초기화된다. |
| 실제 분전함·회로·공동 장애 | 관리 화면의 분전함·회로·시설 이력에서 분전함과 회로를 등록한 뒤 시설을 연결한다. 여러 시설의 장애를 하나로 묶고 신고·작업을 연결한다. 전체 복구는 시설별 확인과 연결 작업의 검수가 필요하다. |
| 점검 응답·전기 측정값 | 8항목을 양호·불량·미실시·해당 없음으로 기록하고 사유를 남긴다. 절연저항과 누설전류는 숫자·단위·측정 시각·작성자를 함께 기록한다. |
| 정기점검 계획 | 담당자, 시설 목록, 반복 주기, 회차별 완료 기간을 정한다. 예정 회차의 작업을 생성하고 미완료 작업은 이어간다. 재시도해도 같은 회차의 작업이 중복 생성되지 않는다. |
| 작업 보류·재개 | 자재·외부 협의·장비·기상·기타 사유, 다음 확인일, 다음 행동을 남긴다. 보류해도 원래 작업 상태와 기한은 유지되며 기한 초과 집계에 포함된다. |
| 구조화한 고장 원인·조치 | 새 작업을 완료할 때 원인과 조치 유형을 선택한다. 기존 작업은 이전 계약을 유지하고, 신규 작업부터 두 값의 입력을 확인한다. |
| 부품 교체 이력 | 시설별 교체 부품, 날짜, 제조사·모델, 보증 종료일과 관련 보수 작업을 기록한다. 교체 이력은 덮어쓰지 않으며 재고를 별도로 차감하지 않는다. |
| 출동 자료 준비 | 선택한 작업과 시설, 신고, 최근 점검 3건, 원본 사진, 확인된 회로 자료를 이 기기에 준비한다. 준비 시각·출처·범위·누락을 표시하며 앱 재시작 후 오프라인에서도 조회할 수 있다. |

정기점검은 관리자가 앱에서 회차 생성·다음 회차 진행을 실행한다. 현재 설정에서 서버 예약 작업이나 앱을 닫은 상태의 푸시 발송을 활성화하지 않았다. 알림함은 앱 안에서 조회한다.

## 기존 기록과 입력 보호

- 미응답 점검 항목을 양호로 채우지 않는다. 불완전 점검은 정식 최근 점검일을 갱신하거나 기존 고장·재점검 안내를 해제하지 않는다. 보수 검수와 동시에 점검이 저장돼도 최신 시설 상태를 기준으로 적용한다.
- `light.sw`의 전자식·GPS 등 점멸기 종류는 실제 회로 ID로 사용하지 않는다. 미등록 회로는 별도로 표시하고, 같은 이름의 서로 다른 회로도 각각 집계한다.
- 작업·자산·정기점검은 버전 비교와 변경 이력으로 중복·충돌을 확인한다. 계정·저장소가 바뀐 뒤 늦게 끝난 조회나 저장은 새 계정의 화면·초안을 변경하지 않는다.
- 자산·정기점검 초안은 저장 대기함에서 이어쓰거나 명시적으로 버린다. 다른 탭이 수정한 초안을 덮지 않고 현재 입력을 별도의 복구 초안으로 남긴다. 배정 확인·보류를 저장해도 작성 중인 완료 내용·사진·원인 선택은 보존한다.
- 교체 초안의 연결 작업은 작업 목록 조회가 늦어도 유지한다. 과거 이력을 조회 목록에서 찾지 못해도 현재 연결값을 빈 값으로 바꾸지 않는다.
- 출동 자료는 최대 50개 작업, 원본 사진 100장, 전체 12MiB로 제한한다. 수집 실패·용량 초과·취소 시 이전에 준비 완료한 자료를 유지한다. 저장을 시작한 뒤에는 취소를 막아 화면과 실제 보관 상태를 일치시킨다.
- 준비한 신고에서는 연락처·위치·신고 사진 등 개인 식별 자료를 제외한다. 권한 거부나 인증 오류를 오프라인 자료로 우회하지 않는다. 최근 점검·신고는 준비된 범위를 명시하며 전체 이력으로 표시하지 않는다.
- 지도 타일의 일괄 다운로드는 추가하지 않았다. 서비스 워커는 새 런타임 모듈 8개를 앱 버전에 맞춰 보관한다.

## 저장·복원

새 컬렉션은 `cabinets`, `circuits`, `assetLinks`, `outageIncidents`, `assetReplacements`, `assetOperations`, `preventivePlans`, `preventiveRuns`, `preventiveOperations`, `inspectionDetails`, `inspectionMeasurements`다. 운영 백업과 서버 복원의 대상·필드 검증·관계 검증에 모두 포함했다.

새 점검의 상세 검증과 측정값 검증을 각각 불변 기록으로 분리했다. 본문·상세·측정값·사진·시설 상태는 같은 원자 저장에 포함되며, 문서 간 작성자·시설·시각·내용이 일치해야 한다. 사진 6장·측정값 10개·항목별 사유 8개를 함께 검증하면서 보안 규칙의 요청 한도를 지킨다. 관리자 검수 후 같은 작업을 재시도해도 검수 내용은 유지되고, 불변 기록이 있는 본문을 직접 삭제하거나 내용을 바꿀 수 없다. 기존 점검과 과거 백업은 그대로 읽는다.

복원 시 분전함·회로의 부모 관계, 같은 시설의 관련 작업·신고, 변경 이력의 원본 스냅샷, 정기 회차·작업·처리 기록의 연결을 검사한다. 기존 작업·점검 형식을 계속 읽으며, 새 형식의 잘못된 날짜·측정 단위·완료 판정·알 수 없는 필드는 거절한다.

## 검증 기록

- `node scripts/check.mjs`: 구문·전역 이름 충돌·필수 자산·대장 검증과 Node 회귀 테스트 481/481 통과.
- `.github/workflows/browser.yml`의 브라우저 스크립트 40/40 통과. 신규 3종은 자산 연결·집단 장애·교체 이력, 배정·보류·정기점검, 점검 측정값·재시작 후 오프라인 출동 자료를 확인했다. 최종 저장 구조를 반영한 뒤 직접 영향을 받는 8종도 다시 실행해 8/8 통과했다.
- 실제 Node 22.23.4로 Functions 단위 테스트 9/9, 서버 핸들러 에뮬레이터 7/7, 운영 복원 에뮬레이터 8/8 통과.
- `node scripts/check-emulator.cjs`: Firestore 권한·증빙·원자 재시도 64/64, 서버 7/7, 복원 8/8 통과. 사진 12장·자재 10종·신고 20건을 함께 검수하는 기존 작업 처리량과, 사유 0~8개·측정값 10개·사진 6장의 새 점검 처리량을 확인했다. 실제 Firebase 점검 명령을 에뮬레이터에서 호출해 최대 미실시 점검의 원자 저장과 검수 후 재시도도 확인했다.

브라우저 검사는 로컬 체험 저장소와 제어한 네트워크 실패를 사용한다. 실제 직원 계정·운영 자료·현장 단말의 통신 중단을 검증한 결과는 아니다. 검사 로그는 `D:\Temp\streetlight-v61-*`와 `D:\Temp\streetlight-v61-browser-final\results.json`에 보관했다.

## 운영 연결

`functionsEnabled: false`, 주민 신고 게이트웨이 URL·App Check 미설정 상태를 유지했다. 주민 접수는 기존과 같이 준비 중으로 표시한다. 새 버전을 실제 운영에 적용할 때에는 앱 파일과 Firestore 규칙을 함께 반영해야 한다. 이번 턴에는 운영 데이터·권한·규칙을 변경하지 않았다.
