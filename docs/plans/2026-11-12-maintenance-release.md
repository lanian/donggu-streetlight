# 유지보수 기능 공개 반영 계획

기준 공개 커밋은 `59c2582`(v72)다. 기존 v61 로컬 구현 중 유지보수 기능만 분리해 v73 후보를 만들고, 검증과 서버 규칙 반영이 완료된 뒤 공개 앱을 배포한다. 기본 개발 폴더와 기존 설정·접수대장 미연결 상태를 보존한다.

1. 기본 폴더와 v72 파일을 비교해 실제 차이만 선별한다. 코드·시험·CI·저장 구조 문서와 유지보수 모듈을 별도 작업 폴더에 옮긴다. 과거 배포 문서와 지도·신고 설정은 복사 대상에서 제외한다.
2. 업무, 현장/오프라인, 서버 규칙/백업 복원을 독립 검토한다. 결함은 의미 있는 실패 시험으로 재현한 뒤 수정한다. 수정은 후보에 반영하고 소유 변경만 기본 폴더로 동기화한다.
3. Node 회귀, Node 22 Functions, 로컬 Firestore 규칙·서버·복원 에뮬레이터, 새 세 종류 및 영향받는/전체 브라우저 검사를 수행한다. 실제 운영 자료·인증으로 시험 데이터를 만들지 않는다.
4. Firebase CLI 로그인·프로젝트 접근 권한을 읽기 전용으로 확인한다. 새 규칙이 필요한 앱을 규칙 없이 먼저 공개하지 않는다. 규칙 변경은 기존 데이터 삭제나 권한 확대를 포함하지 않도록 검토하고 확정한 프로젝트에만 반영한다.
5. 서버 복원 호출은 기존 `functionsEnabled:false`와 App Check 미설정 조건을 유지한다. 새 복원 구현은 검사하되 설정을 임의로 활성화하지 않는다. 실제 서버 복원에 필요한 배포 범위는 별도로 확인한다.
6. 필수 서버 반영과 검사 성공 후 공개 메타데이터·캐시를 갱신하고 앱을 push한다. 전체 CI·Pages 성공을 기다린 뒤 공개 자산 해시와 격리 체험 흐름·화면을 확인한다. 서버 접근이 없으면 완성된 배포 후보와 정확한 외부 의존성을 제시하고 공개 버전은 유지한다.

실기기 지도앱 전환·현장 운전·실제 직원 계정의 권한 검증은 합성/에뮬레이터 검사와 구분한다. 실제 접수대장 연결은 승인된 자료가 없어 이번 범위에 포함하지 않는다.
