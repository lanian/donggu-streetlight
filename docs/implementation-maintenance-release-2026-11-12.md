# 유지보수 기능 v73 배포 후보 검증

현재는 `v73-maintenance-prep` 후보이며 공개 앱은 v72다. 기존 v61 로컬 개발분을 공개 기준 `59c2582` 위의 별도 작업 폴더에 분리했다. 기존 지도·차량 노선·주민 신고 화면 연결·접수대장 준비 모듈과 Firebase/지도/주민 설정은 유지한다.

## 포함한 기능

- 배정 확인·긴급/기한 알림함, 작업 보류·재개와 구조화된 원인·조치.
- 실제 분전함·회로 연결, 공동 장애와 시설별 복구 확인, 부품 교체·보증 이력.
- 명시적 점검 응답·사유·전기 측정값과 불변 증빙의 원자 저장.
- 정기점검 계획·회차별 작업 생성과 미완료 작업 재사용.
- 작업·최근 점검·원본 사진·회로 자료의 범위를 표시한 오프라인 출동 자료 준비.
- 새 11개 컬렉션의 보안 규칙·백업·관계/필드 복원 검증.

정기점검은 앱 안에서 관리자가 회차를 생성한다. 닫힌 앱의 푸시 발송·서버 예약 실행은 활성화하지 않는다. 서버 복원은 기존 `functionsEnabled:false`와 App Check 미설정 조건을 유지하므로 직접 실행되지 않는다. 기본 유지보수 저장에는 새 앱과 Firestore 규칙이 필요하다.

## 검토 중 수정한 결함

1. 작업 생성 시 확인 시각 0과 다른 확인자를 함께 기록할 수 있던 규칙을 거절한다. 복원 검증과 규칙의 계약을 일치시켰다.
2. 담당자가 작업 시작과 동시에 다른 사람 명의의 보류 기록을 넣을 수 있던 규칙을 거절한다. 변경한 보류 작성자는 실제 요청자와 같아야 한다.
3. 계정·DB·저장 범위 변경 뒤 대기 중인 점검 초안 저장과 전송 응답이 새 계정의 초안을 변경하던 경로를 차단한다. 확인창 이후 초안·시설·화면·권한도 재확인한다. 동일 세션의 추가 사진·메모·측정값과 기존 작업 ID·시각·재시도 payload는 유지한다.

두 규칙 결함은 실제 로컬 Firestore에서 수정 전 잘못된 요청이 허용되는 것을 확인한 뒤 수정했다. 점검 소유권은 12개 실패를 재현한 뒤 신규 14개와 기존 7개를 함께 통과시켰다. 별도 검토자가 수정과 시험 경계를 재검토했다.

## 실제 공개 반영 전 조건

현재 Firebase CLI의 연결 계정이 없어 실제 서버 규칙 읽기·반영은 아직 수행하지 않았다. 사용자가 이 PC에서 로그인하는 방식을 선택했고 로그인 명령과 별도 PowerShell 창을 준비했다. 비밀번호·토큰·인증코드를 채팅으로 요청하거나 저장소에 기록하지 않는다.

로그인 후 `donggu-light` 기본 Firestore의 현재 규칙을 읽기 전용으로 내려받아 v72/후보와 비교한다. 승인된 후보와 다른 운영 변경이 있으면 보존·검토한 뒤 반영한다. 필수 규칙이 없는 상태에서 새 앱을 main/Pages에 먼저 공개하지 않는다. 서버 복원 함수나 주민 게이트웨이·예약 작업을 임의로 활성화하지 않는다.
