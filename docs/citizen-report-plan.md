# 주민 신고 운영 안내

이 문서는 초기 분리 계획을 현재 구현에 맞춰 갱신한 안내입니다. 주민은 로그인 없는 `report/` 페이지를 사용하며 직원 대장·사진·순찰 경로를 조회하지 않습니다. 직원은 본 앱의 **신고함**에서 접수 내용과 처리 상태를 관리합니다.

**현재 기본 설정에는 접수 서버와 실제 문자·이메일 수신처가 없습니다.** 코드 구현과 실제 운영 연결은 구분하며, Firebase·App Check·Functions·예약 작업의 운영 배포는 별도입니다.

## 전달 방식 선택

| 방식 | 설정 | 주민에게 표시하는 결과 |
|---|---|---|
| 미설정 | `backend: null`, `sms`·`mail` 비어 있음 | 접수 준비 중. 접수 버튼과 예시 전화번호를 실제 수단처럼 제공하지 않음 |
| 문자·이메일 | 실제 `sms` 또는 `mail` | 외부 앱에 보낼 내용을 준비. 사용자가 직접 전송하고 사진도 직접 첨부. 서버 접수번호 없음 |
| 서버 접수 | `backend: "gateway"`, `gatewayUrl`, App Check와 Firebase 웹 앱 설정 | 서버 저장 성공 후 접수 완료·접수번호 표시 |

이전 `backend: "firestore"`와 공개 Firestore REST 직접 생성 방식은 사용하지 않습니다. 서버 규칙에서 직접 생성을 막으므로 페이지 설정만 예전 방식으로 바꾸어도 접수되지 않습니다.

## 서버 접수 연결

1. [배포 안내](../deploy/README.md)에 따라 같은 Firebase 프로젝트의 직원 앱·역할·규칙·인덱스·Functions를 준비합니다.
2. 운영 origin을 `PUBLIC_REPORT_ORIGINS`에 등록하고 `REPORT_RATE_SECRET`을 서버 비밀값으로 설정합니다. App Check를 등록하고 실제 도메인에서 토큰 검증을 확인합니다.
3. `report/config.js`에 실제 기관·부서·연락처와 `gatewayUrl`, `appCheckSiteKey`, `firestore.projectId/apiKey/appId`를 넣습니다. 접수 원본 컬렉션 기본값은 `citizen_reports`입니다.
4. 실제 수신처와 보관 기간을 확인한 뒤 별도 검증 환경에서 정상 접수·오류·같은 요청 재시도를 확인합니다. 직원 앱 **QR 신고 가져오기**와 완료 처리까지 이어서 확인합니다.

게이트웨이는 허용 입력, 연락처 동의, 좌표, App Check와 요청 빈도를 확인합니다. 사진을 실제로 디코딩·축소·재인코딩해 메타데이터를 제거합니다. 접수 시각·접수번호·보관 만료는 서버가 정합니다. 동일 ID·같은 내용의 재시도는 합치며, 같은 ID의 다른 내용은 거절합니다.

문자·이메일 방식은 외부 앱에서 실제로 보냈는지 이 페이지가 확인할 수 없습니다. 해당 경로의 접수는 담당자가 직원 앱 신고함에 기록합니다.

## QR과 시설 연결

직원 앱의 **QR 라벨**은 `report/?c=표시번호&lid=시설ID`를 만듭니다. 배포 주소를 확정한 뒤 라벨을 인쇄합니다. 이미 붙인 라벨은 사이트 주소 변경으로 자동 갱신되지 않습니다.

- 유효한 `lid`를 번호·위치보다 우선합니다. 같은 번호를 가진 다른 시설과 구분할 수 있습니다.
- 주민이 번호를 직접 바꾸면 기존 `lid` 연결을 해제합니다.
- 명시된 ID가 삭제되었거나 대장에 없으면 직원 앱에서는 미연결 신고로 보관합니다. 다른 시설로 추정 연결하지 않습니다.
- ID 없는 구형 신고만 번호·가까운 위치를 이용한 기존 연결 경로를 사용합니다. 담당자가 시설 연결을 확인합니다.

## 직원 신고함으로 가져오기

**신고함 → QR 신고 가져오기**는 미이관 원본 전체를 조회하고 원본 ID에 대응하는 고정 신고 ID를 사용합니다. 같은 Firebase 저장소에서는 신고 생성과 원본의 가져오기 표시를 한 transaction에서 처리합니다. 재시도해도 이미 처리 중인 신고의 내용을 초기화하거나 중복 생성하지 않습니다.

이관 뒤 원본의 연락처·사진을 정리하고, 직원 신고함에는 업무 처리에 필요한 내용을 보관합니다. 신고함에서 **완료**로 바꾸면 연락처를 비웁니다. 기존 부분 이관 후 대상 기록이 수정된 경우에는 관리자가 결과를 확인해 이관 상태를 복구해야 할 수 있습니다.

직원 Firebase와 신고 Firebase의 프로젝트 ID가 다르면 잘못된 저장소를 읽지 않도록 가져오기를 막습니다. 다른 지원 백엔드로 옮기는 경로는 신고 서버 관리자만 실행하며 여러 저장소 사이의 원자성은 없습니다. 아티팩트 대상은 안전한 신규 생성 기능이 없어 이 가져오기를 실행하지 않습니다.

## 보관 기간

`report/config.js`의 안내 기간과 서버 `settings/operations.privacyDays` 중 짧은 기간을 신규 신고에 적용합니다. 기본값은 90일입니다. 이관은 원래 `privacyExpiresAt`을 유지하므로 보관 기간을 다시 시작하지 않습니다.

배포된 예약 함수가 만료 신고의 연락처·사진·위치·정확도·UA를 정리합니다. 수동 접수에는 서버 트리거가 만료를 붙입니다. 과거 기록은 운영자가 아래 계획을 확인한 뒤 별도 적용해야 합니다.

```bash
node scripts/backfill-retention.cjs --project PROJECT_ID
```

이 명령은 기본적으로 계획만 출력합니다. 실제 변경은 운영자가 프로젝트·자격증명·대상을 확인하고 `--apply`를 지정했을 때 수행됩니다. 예약 작업의 실행량·실패·재시도에 따라 정리가 지연될 수 있습니다. 자유문에 적힌 개인정보, 내보낸 파일과 기기 캐시는 서버 정리 작업이 자동 판별·삭제하지 않습니다.

세부 권한·감사·빈도 제한과 운영 검증 범위는 [서버 보안·보관 안내](security-operations.md)를 참고하세요.
