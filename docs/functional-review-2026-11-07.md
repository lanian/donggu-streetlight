# 전체 기능 검토와 추가 기능 제안

후속 구현: 아래는 수정 전 검토 기록이다. 사용자의 구현 요청에 따라 v60에서 수정·추가한 내용과 검증 결과는 [구현 기록](functional-implementation-2026-11-07.md)에 정리한다.

검토 대상은 현재 로컬 `v59-reliability` 개선본이다. 사용자의 방침에 따라 현재 설정을 유지하고 실배포는 미정으로 두었다. 이번 작업은 검토·재현이며 기능 코드, 설정, 운영 데이터는 변경하지 않았다.

## 결론

일반 업무에서 재현되는 문제 6개를 확인했다. 가장 먼저 수정할 것은 **야간 점등 확인이 시설 전체 고장·재점검 상태와 정기 점검 시각을 변경하는 문제**다. 이후 위치 기록·복구 취소·진행률·신고 연결·보고서 입력 검증을 수정하는 순서가 적절하다.

기존 회귀 328개는 통과했다. 이번 검토의 추가 사용 시나리오에서 아래 문제를 별도로 재현했으므로, 회귀 통과를 모든 기능이 정상이라는 의미로 해석하지 않는다.

## 재현한 기능 문제

### F-01 · P1 · ‘켜져 있음’이 다른 시설 고장까지 정상 처리

- 상황: 시설이 `고장`, 재점검 사유가 `전선 노출 재점검`인 상태에서 야간 순찰의 **켜져 있음 / 직접 점등 확인**을 저장한다.
- 실제 결과: `status=정상`, `redoNote=null`, `lastInspected=순찰 관찰 시각`으로 바뀐다.
- 영향: 점등만 확인했는데 전선·기둥 등 다른 문제의 재점검 요청이 사라지고, 정기 점검 주기도 다시 시작될 수 있다.
- 원인: 순찰 관찰에서 생성한 점검 결과를 시설 전체 상태와 정기 점검 시각에 그대로 반영한다.
- 수정 방향: 점등 관찰, 전체 시설 판정, 정식 점검 날짜를 구분한다. 기존 고장·재점검의 해제는 정식 점검이나 보수 검수에서 판단하도록 한다. 이전 버전에서 저장 대기 중인 순찰 명령의 재전송도 함께 확인해야 한다.
- 근거: `app/staff-app.js:3075`, `:3076`, `:3077`; 점검 대상 판정은 `app/operations-core.js:76`.

### F-02 · P2 · GPS가 나빠진 뒤 이전 장소에 새 관찰을 저장

- 상황: 정확한 위치 `(35.14,126.92), ±5m`를 받은 뒤 다른 위치의 부정확한 수신 `(35.15,126.93), ±120m`가 도착하고 **여기 어두움**을 누른다.
- 실제 결과: 이전 좌표에 새 정확도 `120m`와 현재 시각을 붙여 기록한다.
- 영향: 기록한 장소가 실제 관찰 장소와 달라져 밝기 재확인·신설 검토의 근거가 잘못 연결될 수 있다.
- 원인: 정확도를 먼저 갱신한 뒤 부정확한 위치를 거절하면서 이전 `pt.pos`는 남겨 두고, 기록 버튼은 그 위치를 사용한다.
- 수정 방향: 좌표·정확도·수신 시각을 하나의 관측값으로 관리한다. 새 위치가 거절되거나 이전 위치가 오래된 경우 기록을 보류하고 위치를 다시 확인하도록 한다.
- 근거: `app/staff-app.js:2834`–`:2844`, `:2986`–`:2990`.

### F-03 · P2 · 순찰 복구 후 ‘취소’가 최신 행동을 되돌리지 않음

- 상황: **고장 표시 → 어두운 지점 기록 → 초안 저장 → 새로고침 → 순찰 복구 → 취소** 순서로 실행한다.
- 실제 결과: 최신 어두운 지점은 남고 이전 고장 표시가 제거된다. 재현 상태는 `marks=1, spots=1`에서 `marks=0, spots=1`로 바뀌었다.
- 원인: 복구 초안에 취소 이력을 저장하지 않으며, 복구용 대체 처리는 고장 표시만 고려한다.
- 수정 방향: 표시·어두운 지점·이전 표시값을 포함한 행동 이력을 복구한다. 직렬화 뒤 객체 참조가 달라지는 점을 고려해 행동 ID나 안정된 식별자로 연결한다.
- 근거: `app/integration.js:28`–`:30`, `app/staff-app.js:2995`–`:2999`.

### F-04 · P2 · 순찰 가능한 시설을 모두 통과해도 진행률 66%

- 상황: 현재 대장에서 자동 GPS 통과가 가능한 정확 좌표 시설을 모두 통과한 상태를 구성한다.
- 실제 결과: 화면과 최근 순찰 범위가 **66% (5416/8242)**로 표시된다.
- 원인: 추정 좌표 2,826개는 자동 통과 그리드에서 제외하지만 진행률 분모에는 포함한다. 동을 바꿀 때의 계산도 같은 기준을 사용한다.
- 수정 방향: 자동 통과 대상과 진행률의 분자·분모를 일치시키고, 좌표 확인이 필요한 시설 수는 따로 표시한다. 과거 통과 이력을 읽을 때도 같은 대상 기준을 적용한다.
- 근거: `app/staff-app.js:2472`, `:2798`, `:2803`, `:2846`–`:2847`, 동 변경 `:1421`.
- 범위: 전체 통과 상태를 모의로 구성한 결과이며 실제 현장 순찰을 수행한 결과는 아니다.

### F-05 · P2 · 성공할 수 없는 새 작업 작성을 끝낸 뒤 충돌로 잠김

- 상황: 이미 진행 중인 보수 작업에 연결된 신고에서 **새 작업으로 작성**을 누르고 제목·담당자를 입력한 뒤 저장한다.
- 실제 결과: 기존 작업 연결 충돌로 저장을 거절하고, 새 초안은 `pending=true`와 잠긴 양식 상태로 남는다. 사용자는 대기함과 초안을 정리해야 한다.
- 원인: 작성 화면은 경로를 허용하지만 저장 명령은 같은 신고를 다른 진행 작업에 연결하지 못하도록 막는다.
- 영향: 기존 신고·작업 연결과 중복 방지는 보존되지만 사용자는 불필요한 입력과 복구 작업을 하게 된다.
- 수정 방향: 기존 진행 작업 열기를 먼저 제공한다. 이미 연결된 신고를 유지한 신규 작업 작성은 시작 전에 설명하고 차단한다. 작성 중 다른 직원이 연결한 경우에는 최신 작업을 확인하고 입력을 복구할 수 있어야 한다.
- 근거: `app/workflows.js:91`, `:153`, `app/work-commands.js:80`.

### F-06 · P2 · 거꾸로 된 보고서 기간으로 0건 보고서·CSV 생성

- 상황: 보고서의 직접 기간을 시작 `2026-11-07`, 종료 `2026-11-01`로 지정한다.
- 실제 결과: 오류가 표시되지 않고 조회 완료 상태가 된다. 0건 보고서를 표시하고 `동구가로등_보고서_20261107-20261101.csv`도 생성한다.
- 영향: 입력 실수를 실제 실적 0건으로 오인할 수 있다.
- 수정 방향: 조회·인쇄·CSV가 같은 기간 검증을 사용하도록 한다. 잘못된 기간에는 결과와 내보내기를 막고, 올바른 기간으로 바꾸면 정상 조회를 이어 가야 한다.
- 근거: `app/staff-app.js:1740`–`:1759`, `:1889`–`:1896`. 실제 Chromium과 별도 VM에서 재현했다.

| 3 | 추정 좌표 정비 전용 목록 | 추정 좌표 2,826개를 동·분전함별로 나누어 담당자가 확인 | 좌표 보정 기능은 이미 있음. 전용 필터·확인 대상 목록·진척 관리가 추가 범위 |

1번 작업 정보 수정의 실제 확인: 관리자에게 배정된 작업 상세의 `woReassign`, `woNewDue`가 모두 없었고 버튼은 **작업 시작 / 작업 취소**였다. `app/operations-core.js:43`–`:46`, `app/operations.js:305`, `:328`이 해당 조건이다. 기본 정보만 바꾸려면 상태를 먼저 바꾸는 우회가 필요하다.

2번 근거는 `app/management.js:108`–`:110`, 4번은 `app/work-commands.js:101`–`:112`, 6번은 `app/operations.js:124`–`:133`과 `docs/navigation.md:113`이다. 단위의 의미가 바뀌는 변경은 과거 수량 해석과 함께 별도로 설계해야 한다.

반복 고장 목록, 중복 신고 후보, 시설 통합 업무 이력, 작업별 초안·재시도, 전체 사진 인쇄는 이미 구현되어 있다. 이 기능들은 신규 기능으로 중복 제안하지 않는다.

## 낮은 우선순위와 확인 범위

- 직접 기간의 종료 시각이 `23:59:59.000`이다. 같은 날 `23:59:59.500` 기록은 선택 기간에서 빠진다. 종료일의 마지막 밀리초까지 포함하는 보완이 필요하다(`app/staff-app.js:1745`).
- 재고 합계의 상한 검증이 없다. 수량 100,000,000에서 +1은 저장되지만 이후 -1은 현재 수량 범위 오류로 거절된다. 일반 재고 규모에서는 드문 경계 조건이다(`app/operations-core.js:281`–`:285`). Firestore 규칙의 상한 불일치로 분류하지 않는다.
- 주민 접수 원본은 현재 JSON 백업 범위에서 제외되며 운영 안내에도 명시되어 있다. 백업 화면에서 미이관 건수와 제외 범위를 보여 주면 ‘전체 백업’에 대한 오해를 줄일 수 있다(`docs/operations-guide.md:157`).
- 신고 자료의 초기 구독은 페이지 제한이 없다. 사진이 붙은 신고가 누적될 때의 다운로드·메모리·화면 성능은 별도 부하 검증이 필요하다. 이번 검토에서 운영 데이터로 부하를 측정하지 않았다.

## 검증과 권장 작업 순서

- 현재 소스의 `node scripts/check.mjs`: 328개 통과.
- 밝기 재확인·외부 자료 반입, 제외 구역, 검토 후보 이동, 주민 신고, 업무 통합, 뒤로가기의 브라우저 검사 6개 스크립트 통과.
- 순찰·신고·보수의 추가 상황은 독립 Chromium 프로필과 대체 GPS·로컬 자료로 재현했다. 처리되지 않은 브라우저 오류는 0개였다. 화면이 정상 동작하면서 잘못된 결과를 저장하거나 실패 경로로 유도하는 문제를 확인했다.
- 보고서 기간은 실제 브라우저 조회·CSV 생성과 VM에서 모두 확인했다.
- 현장 GPS의 절대 정확도, 실제 카메라·센서, 야간 OCR 사진 정확도, 장시간 모바일 오프라인, 실운영 계정 간 동시 사용은 이번 결과에 포함하지 않는다.

임시 진단 파일: `D:\Temp\streetlight-patrol-functional-review.cjs`, `D:\Temp\streetlight-patrol-functional-review-restore.cjs`, `D:\Temp\streetlight-work-functional-review-20261107.cjs`. 운영 Firebase에 접속하거나 배포하지 않았다.

권장 순서는 **① 재현된 6개 오류 수정 → ② 작업·자재 정보 수정과 좌표 정비 목록 → ③ 예정 자재·순찰 계획·일괄 처리**다. 실배포 결정과 분리해 로컬에서 구현·검증할 수 있다. 이 보고서의 기능 제안은 아직 구현하지 않았다.
