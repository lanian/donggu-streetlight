# 업무 운영 안내

이 안내는 직원 앱의 현재 화면과 저장 동작을 설명합니다. localhost·loopback 실행은 이 기기에만 저장되는 체험 모드입니다. 호스팅된 직원 앱은 명시된 Firebase 프로젝트와 직원 역할로 공유 저장을 사용하며, 서버 관리 함수와 주민 접수 게이트웨이는 별도로 연결·배포합니다.

## 1. 근무 시작과 기기 선택

1. 현장 전용 휴대폰이면 **사용자·권한 → 이 기기의 저장 방식 → 현장 전용 기기·오프라인 자료 보관**을 선택합니다. 공유 PC는 기본 공유 모드를 유지합니다.
2. **저장 대기함·초안**에서 이전 미전송 작업과 작성 내용을 먼저 확인합니다. 전용 기기에서는 같은 계정·프로젝트로 다시 열면 복구할 수 있습니다. 공유 모드의 초안·대기 작업은 새로고침하거나 현재 창을 닫으면 사라집니다.
3. **미점검·방문 계획**에서 담당 동과 필요한 상태를 선택합니다. 점검 주기는 기본 **90일**이며 관리자가 **업무 기준·보관 기간**에서 바꿀 수 있습니다.
4. 오프라인 작업 전 앱·대장·OCR 준비 상태와 필요한 업무 자료를 확인합니다. 전용 기기의 캐시도 서버 전체 자료나 영구 백업을 의미하지 않습니다.

기기 저장 방식 변경·로그아웃·업데이트 전에 작성 중인 내용과 미전송 작업을 처리합니다. 브라우저 저장 공간을 지우기 전에 완료 기록을 백업하세요. 초안과 대기함은 운영 기록 JSON 백업에 포함되지 않습니다.

## 2. 현장 점검과 순찰

시설을 QR·번호·목록·주변 찾기로 선택하고 위치·대표 사진을 확인합니다. 점검표 8항목, 결과, 메모와 사진 최대 6장을 기록한 뒤 저장합니다. 체크하지 않은 항목은 확인을 거쳐 양호로 채울 수 있습니다. 원본 사진은 시설·작성자·점검 ID와 연결되어 검수 시 다시 확인합니다.

상세 화면을 닫아도 작성 내용은 시설별로 유지됩니다. 저장 중 다른 시설로 이동하거나 메모를 더 수정해도 이전 저장 완료가 새 초안을 지우지 않습니다. 저장 공간 부족은 실패로 표시하며 기존 기록·초안을 유지합니다. 오래된 점검의 재전송은 이력을 남기되 더 최신인 시설 점검 상태를 되돌리지 않도록 처리합니다.

대표 사진은 전경·표찰·주변을 각각 지정합니다. 한 슬롯을 빼도 원본 사진 이력은 남으며 다른 슬롯을 변경하지 않습니다.

야간 차량 순찰에서는 다음 둘을 구분합니다.

- **GPS 근접 통과**: 양호한 GPS 정확도에서 시설 가까이를 지나간 사실입니다. 켜짐·수리 완료·항목별 점검을 뜻하지 않습니다.
- **직접 관찰**: 사용자가 누른 정상·고장·점검필요 표시입니다. 이미 정상인 시설도 직접 점등 확인을 남길 수 있습니다.

직접 점등 확인만으로 기존 고장·재점검 사유를 해제하거나 정기 점검 날짜를 갱신하지 않습니다. 고장 관찰은 경보를 높일 수 있지만 더 최근의 보수 결과를 덮지 않습니다. 진행률의 GPS 통과 대상에는 정확한 좌표가 있는 시설만 포함하며, 추정 좌표는 별도로 표시합니다. 부정확하거나 오래된 위치에서는 **여기 어두움** 기록을 보류합니다.

현장 목록의 **추정 좌표 정비**에서 동·분전함별 확인 대상을 골라 기존 위치 보정 화면으로 이동할 수 있습니다. 방문 계획의 **이 계획으로 야간 순찰**은 아직 확인하지 않은 시설을 순찰 목표로 불러옵니다. 목표 확인은 직접 관찰을 기준으로 하며 단순 GPS 통과와 구분합니다. 종료 화면에서 빠진 목표를 확인하고 다음 순찰로 이월할 수 있습니다. 이월 대상은 저장 대기함에서 다시 열거나 버릴 수 있습니다.

선택한 동은 진행률 기준이며 범위 밖의 고장 관찰도 기록할 수 있습니다. 순찰을 끝내면 경로·통과·관찰을 검토하고 저장합니다. 복구한 순찰은 위치 기록을 정지한 상태로 열립니다. 재시도는 같은 순찰과 연결 점검 ID를 사용합니다.

**여기 어두움**으로 남긴 지점만 있어도 순찰을 저장할 수 있습니다. 시설 통과나 고장 표시가 없어도 위치·관찰 시각·GPS 정확도와 주변 시설 정보가 남습니다. 이 지점은 시설 고장이나 조도계 실측을 확정한 기록은 아닙니다.

순찰 결과의 지점에서 **현장 밝기 기록으로**를 누르면 좌표·관찰 시각·순찰 원본 연결을 이어 받아 관찰을 작성합니다. 실제로 본 밝기와 야간 확인 여부, 적용 시간대를 확인하고 저장합니다. 순찰 기록에서 넘어왔다고 야간 확인이 자동으로 체크되지는 않습니다. 필요한 지점은 **밝기 재확인 업무**로 연결해 담당자와 기한을 정할 수 있습니다. 대장에 없는 시설을 발견한 경우에는 **미등록 양식에**를 사용합니다.

## 3. 저장 대기함에서 복구하기

**저장 대기함·초안**에서 상태를 확인합니다.

| 상태 | 처리 방법 |
|---|---|
| 대기 | 연결을 확인합니다. 앱을 다시 열거나 온라인으로 돌아오면 전송을 이어 갑니다. |
| 전송 중 | 결과를 기다립니다. 화면의 대기 시간 종료가 서버 저장 취소를 뜻하지 않습니다. |
| 실패 | 권한·저장 공간·입력 오류를 확인한 뒤 같은 항목을 재시도합니다. |
| 충돌 | 다른 변경 또는 다른 내용의 동일 작업 ID가 확인된 상태입니다. 최신 업무 내용을 다시 확인하고 처리합니다. |
| 완료 | 서버 또는 기기 저장이 확인됐습니다. 완료된 대기 항목의 사진·연락처 payload는 정리됩니다. |

재시도는 최초 제출한 ID와 내용으로 실행됩니다. 이미 제출한 내용을 바꾸려면 기존 항목의 처리 결과를 확인한 뒤 새 변경을 작성합니다. 대기 항목 폐기는 서버에서 이미 저장된 문서를 취소하거나 삭제하지 않습니다. 초안 폐기는 별도 작업입니다.

Firebase의 보수·재고·대장 갱신은 최신 상태를 확인하는 transaction을 사용하므로 서버 연결이 필요합니다. 전용 기기에서는 해당 명령을 보관하고 연결 후 재시도합니다. 기본 점검·순찰과 아티팩트 저장도 대기함에서 완료 여부를 확인합니다.

보수 작업의 신규 초안과 완료 작성 초안은 작업별로, 밝기 재확인 초안은 업무별로 표시됩니다. **이어쓰기**는 해당 항목을 열며 다른 작업의 초안으로 바꾸지 않습니다. 사진 변환 중에는 원래 작성 화면에 사진을 보관하고, 전송 중인 명령은 제출 당시 내용으로 잠급니다. 저장 공간 부족 등으로 전송 항목 자체를 만들지 못했다면 잠금이 풀리므로 공간을 확보한 뒤 다시 저장합니다. 전송 항목이 만들어진 실패·충돌은 대기함에서 결과를 확인합니다.

## 4. 보수 작업·자재·완료 검수

기기 저장 또는 Firebase 모드에서 사용합니다. 아티팩트에서는 원자적 조건부 저장을 제공하지 않아 이 업무를 실행하지 않습니다.

1. 관리자가 **보수 작업 → 작업 지시 등록** 또는 시설 상세의 **보수 작업 지시**를 엽니다. 시설, 제목, 유형, 우선순위, 담당자, 기한과 관련 신고를 선택합니다. 조치 전 사진은 최대 6장입니다.
2. 배정된 점검자가 **작업 시작**을 누릅니다. 조치 내용, 조치 후 사진 1~6장, 사용 자재와 필요 시 조도계 실측값을 기록하고 **완료 검수 요청**을 보냅니다.
3. 관리자가 원본 사진·내용·자재를 확인합니다. **검수 승인** 또는 사유를 적은 **보완 요청**을 선택합니다. 승인 시 시설 상태 변경과 연결 신고 완료 처리는 선택 사항입니다.
4. 작업·사진·재고·선택한 시설/신고·처리 이력은 함께 반영합니다. 조회 후 변경된 작업·사진·시설·신고·재고가 발견되면 저장을 거절하므로 최신 화면을 확인합니다.

상태는 **배정 대기 → 배정됨 → 작업 중 → 검수 대기 → 완료**입니다. 관리자는 취소·보완·재배정을 처리할 수 있습니다. 재배정해도 이전 처리 이력은 남습니다.

관리자는 미완료 작업 상세의 **작업 정보 수정**에서 상태를 유지하면서 제목·내용·종류·우선순위·담당자·기한을 정정할 수 있습니다. 검수 대기의 실제 자재는 보완 요청 후 수정합니다. 작업 목록에서 원하는 행을 직접 선택하면 담당자·기한·우선순위를 일괄 수정할 수 있고, 작업별 성공·대기·충돌 결과를 확인할 수 있습니다. 이미 진행 중인 작업에 연결된 신고는 **연결된 작업 열기**로 처리합니다.

작업 등록과 정보 수정에서 예정 자재를 입력합니다. **자재 재고**의 부족 예상은 전체 미완료 작업에 저장된 자재를 합산한 조회 시점의 예상이며, 재고를 예약하거나 미리 차감하지 않습니다. 자재명·기준 단가는 사유와 함께 수정할 수 있고 수량·단위·과거 작업 비용은 유지됩니다. 자재 수정 초안은 해당 자재 또는 저장 대기함에서 이어 쓰거나 버릴 수 있습니다.

사용 자재는 총 30행까지이며, 재고와 연결하는 서로 다른 자재는 최대 10종입니다. 한 번의 검수에서 변경되는 재고 ID는 이전 출고분 반환까지 합쳐 최대 10개입니다. 연결 신고는 최대 20건입니다. 사진과 재고가 유효하지 않거나 출고량이 재고를 넘으면 검수가 완료되지 않습니다.

**자재·재고**에서 관리자가 품목을 등록하고 입출고 사유를 남깁니다. 보수 자재의 출고는 완료 요청이 아니라 관리자 검수 시 반영됩니다. 재검수에서는 이전에 반영한 수량과의 차이만 출고·반환합니다. 같은 명령의 재시도는 출고를 반복하지 않습니다.

### 작업별 초안과 여러 탭

새 작업을 시작해도 이전 작업의 초안을 덮어쓰지 않습니다. 입력을 자동 보관하고 화면을 바꾸기 전에 저장을 이어 갑니다. 다른 작업으로 이동한 뒤 도착한 이전 저장·사진 처리 결과는 원래 작업에만 반영합니다. 사진 처리 중에는 완료를 기다린 뒤 제출합니다.

같은 초안을 여러 탭에서 편집하면 저장 버전을 비교합니다. 먼저 저장된 초안을 뒤의 탭이 덮어쓰지 않으며, 보수 작업의 뒤늦은 입력은 별도 복구 초안으로 보존합니다. **저장 대기함·초안**에서 두 내용을 확인하고 사용할 내용을 정합니다. 이는 두 내용을 자동 병합하거나 동일한 보수 작업을 중복 생성한다는 뜻이 아닙니다. 실제 제출 시에도 서버의 작업 버전을 다시 확인합니다. 밝기 재확인 초안은 충돌 화면에서 **최신 초안 다시 열기** 또는 **현재 입력을 새 업무 초안으로 복사**를 선택합니다.

초안 보관과 업무 제출 완료는 별개입니다. 전용 기기인지 현재 창에서만 보관하는 모드인지 먼저 확인하고, 공유 PC에서는 창을 닫기 전에 제출 결과를 확인합니다.

### 오늘 처리할 작업과 방문 계획

**보수 작업**에서 다음 조건을 조합합니다.

| 조건 | 용도 |
|---|---|
| 상태 | 진행 중 전체, 특정 처리 단계 또는 전체 이력 |
| 오늘 기한 | 한국 시간의 오늘 날짜에 기한이 있는 작업 |
| 기한 초과 | 조회 기준 시각보다 기한이 지난 작업 |
| 긴급만 | 우선순위가 긴급인 작업 |
| 내 담당 | 현재 로그인한 직원에게 배정된 작업 |
| 동 | 선택한 동에 속한 시설의 작업 |

화면은 필요한 범위를 나누어 조회하며 **더 보기**로 이어 봅니다. 동 조건에 맞는 작업을 찾기 위해 다음 범위를 계속 조회하므로 첫 화면에 받은 일부 작업만 걸러 전체인 것처럼 표시하지 않습니다. 표시한 건수와 더 조회할 자료가 있는지를 함께 확인합니다.

목록의 **CSV**, **지도**, **방문 계획**은 같은 선택 조건의 전체 작업을 다시 확인합니다. 화면에서 아직 펼치지 않은 작업도 포함하며, 전체 조회에 실패하면 일부 자료로 결과를 만들지 않습니다. 같은 시설에 작업이 두 건 있으면 지도에는 시설 하나, 방문 계획에는 방문 한 번으로 묶고 연결된 작업들을 모두 표시합니다. 작업별 조치와 완료 처리는 각각 수행합니다. 방문 계획은 이동 순서를 돕는 자료이며 도로 통행 조건을 반영한 내비게이션 경로는 아닙니다.

### 신고를 확인한 시설·기존 작업에 연결하기

1. 관리자는 **신고함**에서 **시설 연결·정정**을 엽니다. 표찰 번호·위치로 후보를 찾고 필요하면 시설 후보 지도를 확인합니다.
2. 실제로 확인한 시설을 선택하고 연결·정정 사유를 적어 저장합니다. 신고 원문·접수번호·연락처는 유지하고, 연결 전후 시설·사유·처리자를 이력에 남깁니다.
3. **작업 연결**에서 원래 신고의 선택 여부를 확인합니다. 같은 시설·신고 유형으로 가까운 시기에 들어온 신고가 중복 후보로 제시되지만 자동 선택·삭제·병합되지는 않습니다. 담당자가 원문을 확인한 뒤 함께 처리할 신고만 선택합니다.
4. 기존 미완료 작업을 선택해 연결하거나 **선택 신고로 새 작업**을 엽니다. 새 작업으로 넘어가도 선택한 신고가 유지됩니다. 한 작업에 연결할 수 있는 신고는 최대 20건입니다.

다른 미완료 작업에 이미 연결된 신고를 다시 가져오거나 진행 중인 작업을 둔 채 다른 시설로 옮기는 변경은 거절합니다. 먼저 기존 작업의 실제 처리 상태를 확인합니다. 같은 명령의 재시도는 신고나 연결 이력을 중복 생성하지 않습니다.

### 시설의 통합 업무 이력

시설 상세에서 현재 진행 중인 작업의 담당자·상태를 확인하고 **통합 업무 이력**을 엽니다. 점검·순찰 직접 관찰, 신고 접수와 시설 정정, 보수 작업의 배정·처리·완료 검수, 자재 입출고, 시설 정보 변경을 시간순으로 조회합니다. 현재 작업의 기한과 조치 전후 사진 개수도 함께 표시합니다.

**작업·증빙 열기**에서 원본 사진을 확인하고, **최신 이력 조회**로 갱신합니다. **전체 이력 CSV**와 **인쇄 / PDF**는 조회한 전체 이력과 자료 출처를 포함합니다. 통합 이력의 사진 개수 표시는 원본 사진 첨부를 대신하지 않으므로 사진을 포함한 제출 자료는 사진 부록이나 시설의 이력서 출력에서 확인합니다.

## 5. 보고서와 비용 읽기

**보고서**는 기간·동별 점검, 순찰, 불량 항목, 사진 증빙을 인쇄·CSV·요약 공유로 제공합니다. 화면·공유·CSV는 같은 선택 조건을 사용합니다. 기본 이력 화면의 최근 40건은 미리보기이며 전체 기록을 추가 조회할 수 있습니다. Firebase에서 완전한 보고서와 백업을 만들려면 서버 연결이 필요합니다.

### 사진 부록

**사진 부록**을 켜고 **이상 건만 / 기간 내 전부**와 사진 크기를 선택합니다. 작은·보통 크기의 화면 미리보기는 한 쪽 48장, 큰 크기는 24장입니다. 전체 선택 장수와 현재 미리보기 범위를 표시하고 **이전 사진 / 다음 사진**으로 이동합니다.

**인쇄 / PDF 저장**은 현재 미리보기 쪽에 상관없이 선택한 기간·동·사진 범위의 전체 사진을 준비합니다. 조치 전후 사진은 같은 작업·점검에 연결된 경우에 묶습니다. 출력 준비 중에는 완료를 기다립니다. 원본을 가져오지 못하면 보관된 미리보기로 대체했는지 사진마다 표시하며, 이미지 자체를 표시하지 못한 경우에도 실패 안내가 출력물에 남습니다. **원본 다시 조회**로 재시도하고 필요한 증빙이 모두 확인됐는지 검토합니다.

### 조회 시점과 집계

**업무 현황**의 지표는 다음 의미입니다.

| 지표 | 기준 |
|---|---|
| 기간 점검·점검 시설·작업 접수 | 선택 기간의 점검 시각·작업 생성 시각 |
| 기간 검수 완료 횟수 | 기간 안의 `workEvents` 검수 이벤트 수. 같은 작업의 재검수도 한 번으로 추가 |
| 검수까지 평균 소요일 | 각 검수 시각에서 그 작업의 최초 생성 시각을 뺀 기간의 평균 |
| 기간 자재비 증감 | 검수 이벤트의 `costDelta` 합계. 이전 이벤트에 해당 필드가 없으면 `costTotal` 사용 |
| 현재 미완료·기한 초과·미처리 신고 | 조회 시점의 현재 업무 상태 |

작업에는 마지막으로 인정한 비용 `accountedCost`가 남습니다. 최초 검수 200원, 재검수 300원, 이후 50원으로 정정했다면 이벤트 증감은 **+200, +100, −250원**, 누적 인정 비용은 **50원**입니다. 음수는 이전 비용의 정정입니다. 재배정해도 지난달 검수 실적은 사라지지 않습니다. 이 값은 입력한 자재 수량·단가에 따른 업무 집계이며 결제 기록은 아닙니다.

업무 현황은 날짜를 바꾼 뒤 **기간 조회**를 누릅니다. 오프라인에서는 보관된 자료임을 표시하므로 공식 보고에 쓰기 전 온라인에서 다시 조회합니다.

조회 결과의 출처와 시각은 그 조회에 고정됩니다. 이후 네트워크가 연결됐다고 이미 읽은 캐시가 서버 최신 자료로 바뀌어 표시되지는 않습니다. 서버 자료, 기기에 보관된 캐시, 여러 출처가 섞인 자료, 로컬 체험 자료를 구분합니다. 이전 결과가 남아 있더라도 새 기간이나 조건의 전체 조회가 실패하면 그 결과로 업무 현황 CSV·인쇄를 만들 수 없습니다. 오류를 해결하고 **기간 조회**를 다시 실행합니다.

### 감사 이력과 공유 운영 상태

**감사 이력**은 최근 기록부터 40건씩 읽고 **이전 기록 더 보기**로 이어 봅니다. 조회 오류 뒤에는 **다시 조회**를 눌러 재시도합니다. 화면을 다시 그리는 동작만으로 오류 요청을 계속 반복하지 않습니다. **전체 CSV**는 화면에 펼친 건수와 무관하게 전체 이력을 조회한 뒤 내려받습니다. Firebase에서는 배포된 서버 감사 함수가 만든 기록이고, 로컬 체험에서는 보수 작업 처리 이력임을 구분합니다.

**공유 운영 상태**에서 주민 접수·감사 처리·보관 기간 정리 상태와 처리 대기를 확인합니다. Firebase 및 관련 서버 함수가 설정된 환경에서 조회하며, 미설정 환경은 설정이 필요하다고 표시합니다.

## 6. 대장 갱신 비교

1. 관리시스템 원본은 먼저 `node scripts/build-registry.mjs getPoint.json data/lights.json`으로 변환합니다. 화면에서는 컬럼형 JSON 또는 시설 배열을 받습니다.
2. **대장 갱신 비교**에서 파일을 선택하고 신규·변경·누락·충돌 내역을 확인합니다. 전체 비교 CSV를 내려받을 수 있습니다.
3. 기본값 **현장에서 수정한 값은 유지**를 확인합니다. 새 파일에 빠진 시설은 기본적으로 유지하며, 필요할 때만 철거 표시 옵션을 선택합니다.
4. 적용하면 시설 ID와 연결 이력은 유지됩니다. 표찰 변경 전 번호는 검색 별칭에 남고, 마지막 가져오기 값은 다음 갱신의 비교 기준이 됩니다.
5. 중간 실패 시 저장 대기함에서 같은 작업을 재시도합니다. 80개 단위로 반영하며 이미 완료된 청크는 반복하지 않습니다. 새 현장 변경과 충돌하면 다시 비교해야 합니다.

화면에서 적용한 내용은 운영 기록에 저장되며 저장소의 `data/lights.json`을 직접 고치지 않습니다. 새 설치의 기본 대장도 바꾸려면 변환 결과를 별도로 검토해 배포합니다.

## 7. 백업·복원·이전

1. 미전송 작업부터 처리한 뒤 **백업·이전 → 전체 JSON 내려받기**를 선택합니다. 사진 포함 여부를 확인합니다.
2. 대상 환경에서 파일을 고르고 **복원 내용 검토**로 추가·건너뜀·덮어쓰기·제외 건수를 확인합니다.
3. 기존 문서는 기본적으로 건너뜁니다. 필요한 경우에만 덮어쓰기와 사용자 역할 복원을 별도로 선택합니다. 계정 UID가 달라지면 역할을 새 계정에 맞춰 확인합니다.
4. **검토한 내용 가져오기**를 실행합니다. 실패가 있으면 내려받은 실패 목록을 확인한 뒤 같은 파일로 다시 시도합니다.

대상 컬렉션은 `lights`, `lightFields`, `inspections`, `reports`, `reportEvents`, `patrols`, `roles`, `photos`, `workOrders`, `workEvents`, `auditEvents`, `settings`, `inventory`, `inventoryMoves`, `lightingContext`, `lightingOperations`, `lightingTasks`, `lightingRuns`, `lightingWorkflowOperations`입니다. 사진은 선택 사항입니다. 배포 대장, 도로 캐시, 초안·대기함, `users`, `meta`, 직원 신청·초대와 주민 접수 원본은 이 백업에 포함되지 않습니다.

Firebase 복원은 서버 감사 이력과 아티팩트 변경 로그를 제외하고, 로그를 합친 시설 상태를 사용합니다. 역할은 명시적으로 선택할 때만 복원합니다. 아티팩트에는 안전한 최초 생성 API가 없어 **기존 문서를 보호하는 무덮어쓰기 복원은 실행할 수 없습니다**. 덮어쓰기를 선택하면 기존 값이 교체되므로 대상 환경을 먼저 확인합니다.

Firebase의 **보수·재고·신고 연결 이력·재확인 업무·검토 실행 이력**은 관리자 서버에서 미리 검증한 뒤 한 번에 복원합니다. 연결 신고·작업 사진·점검 원본 사진·완료 근거 관찰도 함께 확인합니다. 원작성자는 유지하고 복원한 관리자는 별도 이력에 기록합니다. 재고 수량과 인정 비용은 백업 상태를 검증해 복원하며 출고·검수 명령을 다시 실행하지 않습니다. 기존 불변 이력의 다른 내용 덮어쓰기와 이전 revision으로 되돌리기는 거절합니다.

이 업무 묶음은 **200문서·4MB 이하**, 미리보기는 **15분 유효**입니다. 서버 기능 미설정·초과·누락 증빙은 일반 자료를 쓰기 전에 알려 줍니다. 미리보기 뒤 대상 자료가 변경되면 **현재 자료와 다시 비교**합니다. 응답을 못 받았다면 같은 계획으로 다시 가져와 완료 영수증을 확인할 수 있습니다. 파일과 옵션은 검토·적용 중 변경할 수 없습니다. 일반 자료는 업무 묶음 다음에, 역할은 맨 마지막에 복원합니다.

큰 자료는 운영자가 [관리자 대량 이전 도구](security-operations.md)를 사용합니다. 확인한 관리자 1명만 있는 빈 업무 저장소가 대상이며 계획 검토 뒤 명시적으로 적용합니다. 중단되면 같은 파일·작업 ID로 재개하고, 완료 확인 전까지 일반 업무 조회·편집은 잠깁니다. 임의로 잠금을 지우지 않습니다.

업무 묶음과 독립된 외부 광원·현장 관찰(`lightingContext`)은 현재 revision을 확인한 새 명령으로 복원합니다. 기존 생성자는 유지하고 신규 문서는 복원한 계정으로 생성합니다. 대상에 없는 제외 기록은 되살리지 않습니다. 변경 불가 처리 영수증(`lightingOperations`, `lightingWorkflowOperations`)과 서버 `restoreOperations`, `systemHealth`는 직접 복원하지 않습니다.

백업은 여러 컬렉션을 순서대로 조회하며 전체 데이터베이스의 한 시점 스냅샷은 아닙니다. 업무 묶음 이외의 일반 복원은 문서별이므로 일부 성공 후 실패할 수 있습니다. 복원 파일에는 연락처·사진 등 운영 자료가 들어갈 수 있으며 서버의 보관 기간 정리 작업이 외부 파일까지 지우지는 않습니다.

## 8. 구현된 저장 보장의 범위

- 기기 저장은 IndexedDB transaction으로 다중 탭 변경과 조건부 쓰기를 보호합니다.
- Firebase 점검은 사진·점검·시설 상태 batch, 보수·재고는 transaction을 사용합니다. 큰 순찰은 여러 batch로 나뉠 수 있으며 최종 순찰 문서가 나중에 기록됩니다.
- 아티팩트 점검·순찰은 순차 저장입니다. 중간 결과가 먼저 보일 수 있으나 고정 ID로 이어서 처리합니다. 같은 필드나 이력 배열의 모든 동시 수정에 일반적인 충돌 병합을 제공하지는 않습니다.
- 대장 갱신은 청크 단위입니다. Firebase 웹 업무 복원 묶음은 원자적으로 반영하며 일반 자료는 문서별입니다. 대량 초기 이전은 업무 접근을 잠근 뒤 묶음별로 진행하고 같은 작업으로 재개합니다. 일반 자료의 실패 전 완료 기록을 자동으로 되돌리지 않습니다.
- 현재 전체 조회 API는 제한된 결과를 완료로 표시하지 않지만, 아티팩트 서버가 잘림을 알리지 않고 자료를 제한하면 클라이언트에서 이를 증명할 방법은 없습니다.

주민 신고와 개인정보 보관은 [주민 신고 안내](citizen-report-plan.md), 계정·서버 감사·전용 기기 설정은 [서버 운영 안내](security-operations.md)를 참고하세요.

## 9. 밝기 예측 근거와 재확인 업무

### 대장에 표시되지 않은 빛 확인

밝기 검토의 상대 모델 값은 실제 밝기의 확정값이나 조도계 실측값이 아닙니다. 대장에 없는 타기관 가로등, 상가·건물·공동주택의 빛 때문에 현장이 더 밝을 수 있습니다. **대장 밖 광원·현장 밝기**에서 광원의 관리 주체·위치·점등 시간·확인 시각을 보완하고, 실제로 밝음·보통·어두움으로 본 관찰과 조도계 실측은 별도 근거로 기록합니다.

확인할 한국 시간대를 선택해 검토하면 대장 모델, 유효한 외부 광원을 반영한 값, 현장 관찰을 구분해 표시합니다. 시간대가 맞지 않거나 야간·점등이 확인되지 않은 광원, 유효기간이 지난 근거는 확인이 필요한 자료로 남습니다. 현장 관찰은 모델 지수에 임의의 밝기 수치로 더하지 않습니다.

### 밝기 재확인 업무

1. 검토 후보, 순찰 지점, 유효기간이 지난 광원·관찰에서 업무를 연결하거나 **밝기 재확인 업무 → 지점 재확인 등록**을 사용합니다. 대장 시설 ID가 없는 지점도 좌표로 등록할 수 있습니다.
2. 제목·확인 범위·담당자·기한과 현장에서 확인할 시간을 정합니다. 날짜와 시간은 한국 시간 기준입니다. **진행 중 / 내 진행 업무 / 기한 초과 / 완료 / 취소 / 전체**로 찾아봅니다.
3. 현장에서 새 밝기 관찰을 저장합니다. 순찰·업무에서 가져온 위치와 시각을 검토하고 야간 확인 여부와 적용 시간대를 직접 지정합니다.
4. 업무를 다시 열어 그 업무 이후의 유효한 관찰을 연결하고 확인 결과·다음 조치를 적은 뒤 완료합니다. 업무 등록보다 5분 넘게 이른 관찰, 선택한 확인 시간을 포함하지 않는 관찰, 야간 확인이 없거나 유효기간이 지난·제외된 관찰은 완료 근거로 쓸 수 없습니다. 위치도 업무 확인 범위와 관찰 반경이 닿는 범위여야 합니다.

완료는 현장 밝기를 확인했다는 뜻이며 시설 상태 변경이나 보수 완료를 자동 처리하지 않습니다. 완료·취소된 업무의 재개는 관리자가 처리합니다. 초안과 전송 결과는 **저장 대기함·초안**에서도 확인할 수 있습니다. **업무 전체 CSV**는 현재 보기의 첫 화면에 제한하지 않고 전체 업무를 내려받습니다.

### 타기관 조명 자료 반입

관리자는 **외부 광원 가져오기 → 타기관 조명 CSV·GeoJSON 반입**에서 UTF-8 CSV 또는 Point GeoJSON을 선택합니다. 최대 5MB·5,000행이며, 원본 관리기관과 자료 출처·버전을 입력한 뒤 기관 시설 ID·좌표·이름 등의 열을 연결합니다.

**검증·반입 미리보기**에서 신규·기존 보존·파일 중복·입력 오류를 확인하고 **검증된 신규 기록 반입**을 실행합니다. 같은 기관·시설 ID의 기존 기록과 현장 수정은 덮어쓰지 않습니다. 새 자료는 야간·점등·시간 미확인으로 저장되며, 확인 전에는 밝기 수치에 자동 반영되지 않습니다. 일부 행에 오류가 있으면 **전체 검토·처리 결과 CSV**에서 원본 행 번호와 사유를 확인합니다. 실패한 전송은 대기함에서 같은 명령으로 이어서 처리합니다.

### 검토 실행 이력과 관찰 비교

밝기 검토 계산이 끝나면 조건·모델 버전·입력 식별 정보·후보·관찰 비교를 실행 이력으로 보관합니다. **현재 실행 이력 보관 완료 / 전송 대기 / 실패** 표시를 확인하고, 필요한 경우 **현재 실행 이력 보관**이나 대기함에서 재시도합니다.

**밝기 검토 이력** 또는 검토 결과의 **검토 이력·관찰 비교**에서는 대장 모델과 외부 광원을 반영한 모델이 유효한 현장 관찰과 얼마나 일치했는지, 모델상 밝지만 현장에서는 어두웠는지, 모델상 부족하지만 현장에서는 밝음·보통이었는지를 비교합니다. 조건 불충족·충돌로 제외한 관찰도 사유와 함께 확인합니다. 이 비교는 독립된 현장 표본의 정확도나 법정 조도 기준 충족률을 뜻하지 않으며 모델 계수를 자동 변경하지 않습니다.

**전체 근거 보기**, **이 실행 JSON**, **관찰 비교 전체 CSV**에서 전체 내용을 확인할 수 있습니다. 한 실행은 UTF-8 기준 최대 600KB이며 내부 항목별 제한도 적용합니다. 한도를 넘으면 일부만 저장하지 않고 오류를 알리므로 동 등 검토 범위를 나누어 다시 실행합니다. 실행 이력은 당시 입력의 식별 정보와 버전을 보관하는 자료이며 원본 자료 전체의 백업을 대신하지 않습니다.

밝기 근거의 필드와 판정 조건은 [밝기 보완 자료 안내](LIGHTING_CONTEXT.md)를 참고하세요.


## 10. 산·숲 등 검토 제외 구역과 후보 확인

### 조명 검토가 필요 없는 구역 지정

**관리 → 밝기 검토 제외 구역**에서 관리자가 범위를 지정합니다. 검토 후보의 **이 주변 검토 제외**로 들어가면 해당 지점을 중심으로 범위를 작성할 수 있습니다. 기본 반경은 25m이므로 실제 제외할 산림·사유지 경계를 지도에서 먼저 확인합니다.

1. **새 제외 구역**을 누르고 이름과 사유(산·숲, 사유지·단지 내부, 통행로가 아닌 곳, 하천·수면, 기타)를 입력합니다.
2. **중심과 반경**은 지도에서 중심을 누르고 반경 5–1,000m를 정합니다. **경계선을 직접 지정**은 **점 추가** 상태에서 둘레를 순서대로 눌러 3–32개 점으로 지정합니다. 첫 지점을 마지막에 반복하지 않습니다.
   - 점을 다 찍으면 **그리기 마치기 · 모양 수정**을 누릅니다. 이후 지도 바탕을 눌러도 점이 추가되지 않습니다. 기존 다각형은 모양 수정 상태로 열립니다.
   - 번호가 붙은 점을 끌어 위치를 고칩니다. 점을 누른 뒤 **선택한 점 삭제**, 선의 **+**로 중간 점 추가, **되돌리기·다시하기**, **전체 범위 보기**를 사용할 수 있습니다. 점에 키보드 초점을 두고 Enter/Space로 선택, 방향키로 이동(Shift로 크게 이동), Delete로 삭제할 수 있습니다.
   - 좌표가 필요하면 **좌표 직접 입력 · 고급 설정**을 펼칩니다. 잘못 입력한 원문도 초안에 유지되고 되돌릴 수 있습니다. 경계점 전체 비우기는 확인 후 실행하며 되돌리기로 복구할 수 있습니다. 편집 이력은 현재 열어 둔 초안에서 제공하고 새로고침 후에는 저장된 좌표부터 시작합니다.
   - 3점 미만·겹치는 점·교차하는 경계 등은 지도 미리보기와 안내를 보며 수정합니다. 올바른 경계가 되기 전에는 저장과 그리기 마치기를 사용할 수 없습니다.
3. 실제 보행로가 함께 포함되는지 확인하고 **구역 저장**을 누릅니다. 저장 완료 뒤 밝기 검토를 다시 실행합니다.
4. 산 안의 산책로처럼 검토가 필요한 부분은 **보행로 예외 추가**로 좁은 구역을 지정합니다. 겹치는 경우 예외 포함이 우선하며, 도로 자료의 자동 산림·단지·사유지 제외도 그 범위 안에서는 해제합니다. 도로 검토는 현재 불러온 도로망에 있는 길을 대상으로 하며 예외 지정만으로 누락 도로를 새로 만들지는 않습니다.

구역은 도로 검토와 등 간격 검토에 적용합니다. 도로가 경계를 가로지르면 교차점에서 나누어 해당 부분만 제외합니다. 등 간격 검토는 후보 중간점이 지정 구역 안인지 판단합니다. 이는 조명 검토 범위 설정이며 시설·광원·현장 관찰 또는 모델의 밝기 값을 삭제·변경하지 않습니다.

야간·시간대·유효기간을 만족하는 **어두움·관찰 충돌 근거**가 있으면 제외 구역 안이라도 확인 대상으로 표시합니다. 오래되거나 야간 확인이 없는 관찰만으로 제외 설정을 무효화하지 않습니다. 도로 후보는 기존 24m 이상 조건을 유지하며 더 짧은 실제 어두움 관찰은 지점 후보로 확인할 수 있습니다.

**적용 중 전체 / 제외 구역 / 보행로 예외 / 해제한 구역 / 전체 기록**으로 찾아보고 **지도 확인·수정 → 제외 해제·예외 해제 / 다시 적용**으로 되돌립니다. 다른 관리자의 변경이 있으면 덮어쓰지 않고 다시 읽도록 안내합니다. 작성 중인 구역과 미전송 명령은 **저장 대기함·초안**에서 이어 처리할 수 있습니다.

일반 점검자는 저장한 구역을 볼 수 있으며 범위 변경은 관리자만 가능합니다. Firebase에 연결했다면 새 규칙을 먼저 배포해야 합니다. 현재 구역을 읽지 못하거나 잘못된 도형이 있으면 이전 조건으로 계산하지 않고 오류를 알립니다.

### 검토 결과를 빠르게 확인하기

- **장소·동·주변 시설 검색**과 **근거별 보기**를 함께 사용합니다. **현장 어두움·관찰 충돌**만 모아 볼 수 있습니다.
- **확인 우선순위 / 긴 도로 구간부터 / 장소 이름순**으로 정렬합니다. **보기 초기화**는 검색·필터·정렬만 초기화합니다.
- 후보 카드에는 확인할 이유를 먼저 표시하고, 상대 지수·관찰 범위·광원 목록은 **밝기 수치·반영 근거 보기**에서 펼칩니다.
- **지도 확인 → 이전 후보 / 다음 후보**로 현재 보기 순서대로 이동합니다. **검토 목록으로** 또는 휴대폰 뒤로가기로 검색·필터·펼친 목록 길이를 유지한 채 돌아옵니다. 지도에서 다른 후보로 이동했다면 마지막 후보를 강조해 보여 줍니다.
- 전체 지도는 한 번에 200곳씩 표시하며 **이전 200곳 / 다음 200곳**으로 현재 보기 전체를 확인합니다. **현재 보기 CSV**는 화면의 20곳이나 지도의 200곳 제한 없이 현재 검색·필터·정렬에 해당하는 전체 후보를 내보냅니다.
- 지도에는 수동 제외 구역과 예외 포함 경계, 도로 자료의 자동 제외 영역을 표시합니다. 구역 변경 뒤에는 재검토가 필요합니다.

### 제외 근거 보관과 백업

검토 실행의 입력 버전 JSON에는 당시 구역의 전체 범위·사유·revision과 제외 집계를 함께 보관하고 자료 지문에도 반영합니다. CSV에는 제외 구역 안에서도 어두움·충돌 근거로 남긴 후보의 사유를 포함합니다. 중첩된 구역별 길이는 중복될 수 있지만 총 제외 길이는 중복 합산하지 않습니다.

전체 JSON 백업에는 `lightingAreas`와 변경 당시 전체 구역 스냅샷을 가진 `lightingAreaOperations`가 포함됩니다. 복원은 구역마다 현재 revision을 확인하는 새 관리자 명령으로 처리합니다. 변경 영수증은 직접 덮어쓰지 않으며 대상에 없는 해제 기록은 새 구역으로 만들지 않습니다. 검토 이력의 기존 용량 제한은 유지되므로 구역·후보가 많으면 검토 지역을 나누어 실행합니다.

### 가로등 대장 교체 (공공데이터 2026-09-10)

`data/lights.json`의 **가로등**을 공공데이터 "광주광역시 동구 가로등 현황"(관리번호 `동구-분전함-번호`, 기준일 2026-09-10, 3,774건)으로 교체했습니다. 보안등·공원등·특이등은 그대로입니다. 다시 만들 때는 `node scripts/merge-streetlights-csv.mjs 가로등.csv data/lights.json --report 보고서.csv`.

### 앱 업데이트 전 확인 (v42-update-check)

새 버전이 있으면 현장 점검·관리 현황 화면 위에 **새 버전이 있어요 · 새 버전 적용** 안내가 뜹니다(오프라인 준비 패널의 버튼도 같음). 누르면 앱이 먼저 지금 화면의 작성 내용을 이 기기에 보관하고 다음을 판단합니다.

- **아무것도 없으면** 바로 적용하고 새로 엽니다.
- **이 기기에 보관된 것만 있으면**(작성 중이던 점검·보수 작업 등, 보내지 못한 기록) 이름과 건수를 보여 주고 **적용하고 다시 열기 / 나중에**를 묻습니다. 보관된 초안은 업데이트 후 저장 대기함에서 이어 쓰고, 보내지 못한 기록은 연결되면 자동으로 보냅니다.
- **새로 열면 사라질 것이 있으면** "새 버전 적용 전에 확인해요" 화면에 **먼저 마쳐 주세요**(진행 중인 야간 순찰, 사진 편집, 표찰 읽기, 보관되지 않은 입력 양식·신고 입력, 공유 기기 모드의 미전송·초안)와 **그대로 남아요**를 나눠 보여 주고, 항목마다 그 화면으로 가는 버튼(순찰 화면으로·그 화면으로·저장 대기함 열기)이 있습니다. 마친 뒤 **다 마쳤어요 · 다시 확인**을 누르면 적용됩니다. 적용하지 않아도 지금 쓰는 데는 문제가 없습니다.
- 다른 창에서 새 버전을 적용한 경우에도 같은 확인을 거쳐 이 창을 새로 엽니다. 확인을 마친 업데이트는 보관된 초안이 있어도 다시 막지 않습니다.
- 자동 검사: `scripts/update-check-browser-smoke.cjs`, `scripts/tests/pwa.test.cjs`.

### 가림·가설물과 주요 시설 우선순위 (v39-obstruction-poi)

- **가림·가설물 기록**: 관리 → 외부 광원·관찰 관리의 **가림·가설물 기록**(또는 검토 후보의 "광원·가림 보완")에서 공사 가림막·비계, 가로수·수목, 간판·차양·현수막, 기타 구조물을 위치·반경(5–80m)·가리는 정도·남아 있을 기간(최대 365일)으로 기록합니다. 야간 확인·점등 시간·조도는 묻지 않습니다(`kind: 'obstruction'`, `schedule: 'always'`).
- **계산**: 반경 안의 관리 대장 빛(상대 지수)을 조금 가림 25%, 절반쯤 50%, 대부분 75% 줄입니다. 여러 가림이 겹치면 가장 큰 비율 하나만 쓰고, 외부 광원 빛은 줄이지 않습니다. 기간이 지나거나 '검토에서 제외'하면 빠지고 재확인 대상으로 표시됩니다.
- **결과**: 가림이 없으면 기준 이상인데 가림 때문에 부족해진 곳은 **가림·가설물로 부족**(우선순위: 현장 어두움 다음, 모델상 부족보다 앞)으로 분류합니다. 간격이 적정한 등 사이라도 가운데가 가려지면 등 간격 검토 후보가 됩니다. 후보 근거에 "대장 모델 0.10 (가림 전 0.40)"과 가림 기록이 나오고, '근거별 보기 → 가림·가설물 영향'으로 모아 볼 수 있습니다. 검토 지도에는 갈색 원으로, CSV에는 `가림가설물`·`가림전대장지수` 열로 나옵니다.
- **주요 시설 우선순위**: 도로망을 받을 때 OpenStreetMap의 횡단보도, 버스정류장, 학교·유치원·어린이집(점과 학교 부지)도 함께 받습니다. 횡단보도·버스정류장 30m, 학교·어린이 시설 부지 경계 100m 안의 후보는 각각 점수 +25, +20, +30을 받아 목록 앞쪽으로 오고 "횡단보도 12m"처럼 표시됩니다. 밝기 지수는 바꾸지 않습니다. '근거별 보기 → 횡단보도·정류장·학교 주변'으로 모아 볼 수 있고, CSV `주변시설` 열에 들어갑니다.
- 예전에 받아 둔 도로망에는 이 시설 정보가 없습니다. 관리자가 **도로망 다시 받기**를 한 번 하면 공유 저장소에도 함께 올라갑니다.
- **서버 규칙 배포 필요**: 가림·가설물은 `lightingContext`의 새 종류라 `firestore.rules`와 복원 검사(`functions/restore-core.js`)를 함께 바꿨습니다. 웹 배포와 별도로 `deploy/README.md`의 `firebase deploy --only firestore:rules,functions`를 실행해야 공유 저장소에 저장됩니다. 배포 전에는 가림 기록이 서버에서 거부되어 저장 대기함에 남습니다.
- 동구 경계 대체 기준 보완: 동구 경계가 없을 때는 13개 행정동 경계가 **모두** 있을 때만 합쳐 쓰고, 일부만 있으면 관리 시설 300m 기준을 씁니다(빠진 동의 동구 도로가 잘리지 않게).
- 자동 검사: `scripts/tests/lighting-model.test.cjs`(정규화·감소·겹침·외부 광원·기한), `scripts/tests/lighting-area-review.test.cjs`(가림 도로·등 간격 후보, 횡단보도 점수, 행정동 경계 대체), `scripts/tests/firestore-rules.emulator.cjs`(가림 기록 규칙), `scripts/obstruction-browser-smoke.cjs`(입력 화면, 등 간격·도로 검토, 지도·CSV·이력, Overpass 응답의 주요 시설).

### 밝기 예측을 광주 동구로 한정, 검토 이력 보관 개선 (v38-donggu-scope)

- **동구 안만 예측**: 도로망은 사각형 범위(위도 35.095–35.175, 경도 126.895–126.975)로 받아서 남구·북구·서구 도로도 섞여 옵니다. 도로 따라 검토는 함께 받은 **동구 경계** 안의 도로 조각과 현장 관찰 지점만 계산합니다. 동구 경계가 없으면 동구 행정동 13곳 경계를 합쳐 쓰고, 경계 자료가 전혀 없으면 관리 시설 300m 안만 남깁니다. 결과 위에 기준과 "동구 밖 도로 N km 제외"가 표시됩니다. 등 간격 검토는 원래 동구 관리 대장 시설끼리의 짝이라 경계로 다시 거르지 않습니다(경계 근처 대장 시설의 후보가 빠지지 않게).
- 경계 판정은 위도 약 22m 간격 가로줄마다 경계와 만나는 경도를 한 번 구해 두고 찾는 방식이라, 도로 표본이 많아도 느려지지 않습니다.
- **검토 이력 압축**: 이력에 넣는 후보 값을 반올림하고(위치 소수 7자리, 지수 4자리, 길이 0.1m) 빈 목록과 0인 집계는 생략합니다. 실제 대장 기준 후보 하나가 351자에서 192자로 줄어, 한 건에 약 1,560곳까지 담깁니다. 필수 값(이름·위치·대장/외부 반영 지수)은 그대로라 서버 규칙과 복원 검사는 바뀌지 않았습니다.
- **동별로 나눠 보관**: '모든 동' 검토가 한 건(후보 300,000자·전체 600KB)에 담기지 않으면 법정동별 이력으로 나눠 **모든 후보를 한 번씩** 보관합니다. 이력의 검토 지역에는 "전체 중 ○○동 (N개로 나눔)"이 적힙니다. 나눈 동 하나가 그래도 넘치면 아무것도 보관하지 않고, 지금 크기와 함께 동을 좁혀 다시 실행하라고 안내합니다.
- 자동 검사: `scripts/tests/lighting-area-review.test.cjs`(동구 밖 도로·관찰 제외, 행정동 경계 대체), `scripts/tests/lighting-workflows.test.cjs`(압축 행, 1,200곳 한 건 보관, 3,000곳 12개 동 분할), `scripts/brightness-smoke.cjs`(시험 도로망에 동구 경계 추가).

### 밝기 검토 지도 한 번에 보기 (v37-review-map-all)

- 밝기 검토 결과의 **표시 후보 지도**는 기본으로 후보를 **1,000곳**까지 한 지도에 그립니다(이전에는 200곳). 지도 위쪽에서 **200곳 · 1,000곳 · 전체** 중에서 고를 수 있고, 다 들어가지 않으면 이전/다음으로 넘깁니다. 고른 값은 다른 검토 지도를 열어도 유지됩니다.
- 지도 부담은 대부분 동구 전체 등(5천여 개)의 반경 원에서 나옵니다. 실제 대장으로 후보 3,000곳을 그려도 PC 브라우저에서 0.4초 안에 열렸습니다. 오래된 휴대폰에서 느리면 200곳으로 낮추세요.
- '근거별 보기'를 '우선 현장 확인'으로 두고 지도를 열면 문제 후보만 한 화면에 나옵니다.

### 방문 계획 노선 개선 (v36-visit-route)

- **방문 순서 계산**: 같은 시설이 두 번 선택되면 한 방문지로 합치고 연결된 보수 작업도 합칩니다. 내 위치가 있으면 가장 가까운 시설에서 출발하고, 없으면 모든 시설을 출발점으로 시도해 가장 짧은 순서를 고릅니다. 그다음 **2-opt**(교차하는 구간 풀기)와 **Or-opt**(1~3곳 묶음을 더 나은 자리로 옮기기)로 다듬습니다. 200곳 기준으로 단순 근접 순서보다 직선 거리가 약 15% 짧습니다. 여전히 직선 거리 기준이며 도로·일방통행은 반영하지 않습니다(`method: 'straight-line-optimized'`).
- **거리 표시**: "방문지 사이 직선 거리"와 "남은 N곳 거리(내 위치부터)"를 따로 보여 줍니다. 계획을 만들 때의 출발 위치와 첫 방문지까지 거리는 `origin`·`startDistance`에 따로 저장합니다. 15m 안에 붙은 다음 시설은 "앞 시설과 같은 자리"로 표시합니다.
- **다음 6곳 경로**: 남은 방문지 중 앞의 6곳을 지도 앱에 경유지로 넘깁니다(앞 5곳은 경유지, 6번째는 목적지). 휴대폰·태블릿: **네이버 지도 차량**, **카카오맵 차량/도보**(앱 `kakaomap://route`의 `sp`·`vp`~`vp5`·`ep`; 출발은 내 위치, 위치를 모르면 첫 방문지에서 출발), 구글 지도 차량/도보. 네이버·카카오 경로는 앱이 설치된 기기에서만 열립니다. PC: 구글 지도(웹) 차량/도보만 — 네이버·카카오의 웹 지도는 경유지 링크를 지원하지 않습니다.
- **내 위치에서 다시 정렬**: 같은 방식으로 남은 방문지를 다시 계산하고, 직선 거리가 50m 이상 줄면 줄어든 거리를 알려 줍니다.
- **계획 지도**: 번호는 계획 순서 그대로 붙어서 필터로 일부를 숨겨도 번호가 바뀌지 않고, 다음 방문지에 노란 테두리를 둘러 표시합니다. 계획 CSV에는 앞 방문지까지 직선 거리와 자동 완료(점검 완료) 상태가 들어갑니다.
- 자동 검사: `scripts/tests/operations.test.cjs`(출발점, 교차 없음, 단순 근접 순서 대비 단축, 중복 합치기, 200곳 제한), `scripts/visit-plan-browser-smoke.cjs`(다음 방문지 지도 표시, 다음 N곳 경로 URL).

### 미점검·방문 계획 (v33-visit-plan)

- **대상 고르기**: 행정동·점검 상태 필터 아래 **가까운 순으로**(한 번 위치를 받아 거리순 정렬, 거리 표시) · **가까운 10곳 선택**(가까운 순이 아니면 위 10곳) · **보이는 N곳 선택**(최대 200) · **선택 해제**가 있고, 선택 수가 "선택한 N곳 방문 계획" 버튼에 보입니다. 선택은 `DGOperations.state.planPick`에 있어 필터를 바꾸거나 화면이 다시 그려져도 남습니다(폼 복원 대상에서 제외).
- **계획 화면이 맨 위**에 오고 진행 막대(완료/전체)와 **다음 방문지 카드**(번호, 내 위치에서 거리, 점검 상태, 점검하기 · 길찾기 · 방문 완료)가 있습니다. 각 방문지에는 번호, 직전 방문지로부터 직선 거리(+Xm), 점검/보수/위로/아래로 버튼이 있습니다.
- **자동 완료**: 계획을 만든 뒤(`createdAt`) 점검을 저장해 `lastInspected`가 갱신된 시설은 "점검 완료"로 자동 표시되며 수동으로 되돌리지 않습니다. 방문 체크는 별도로 저장되고 점검 결과를 바꾸지 않습니다.
- **내 위치에서 다시 정렬**: 완료된 방문지는 앞에 두고 남은 방문지를 현재 위치부터 가까운 순(최근접 이웃)으로 다시 묶습니다. 계획 시작점은 계획을 만들 때 받은 내 위치입니다.
- **계획 지도**: 방문 순서 번호 마커와 점선 연결선, 완료 방문지는 회색. 마커를 탭하면 정보 카드가 열립니다(`openMap('custom', {ordered:true, done:[…]})`).
- 자동 검사: `scripts/visit-plan-browser-smoke.cjs`(거리순 선택, 계획·다음 방문지·구간 거리, 방문 완료·자동 완료, 재정렬, 번호 지도, 길찾기, 재시작 보존), `integration-ui-smoke.cjs`(기존 선택·방문·순서 보존).

### 지도 보기 (v32-map-view)

- **멀리서는 묶음, 가까이서는 번호.** 줌 15 이하에서는 화면 격자(72px)마다 등을 묶어 개수 원으로 보여 주고, 조치 필요(정상 아님) 수를 노란 배지로 붙입니다(묶음의 20% 이상 또는 10개 이상이면 빨간 원). 묶음을 탭하면 그 범위로 확대됩니다. 줌 16부터는 등마다 마커, 줌 18(밀집한 곳은 19)부터는 마커 옆에 표찰 번호 라벨이 붙습니다. 마커는 현재 화면(여유 25%) 안의 등만 그려 5천여 개도 매끄럽게 움직입니다.
- **필터**: 종류 칩 아래 상태 칩(고장·점검필요·수리중·정상·주기 경과)이 있고, 아래 범례의 상태를 탭하면 그 상태를 잠시 숨기거나 다시 보입니다. 필터·검색어·선택한 등은 지도에서 다른 화면을 열었다 돌아와도 유지됩니다.
- **검색과 내 주변**: 지도 위 검색창에 표찰 번호·주소·전주번호를 입력하면 최대 8건이 뜨고, 탭하거나 Enter로 첫 항목을 고르면 그 등으로 확대하며 카드가 열립니다. **내 주변**은 내 위치 기준 300m 안의 등을 거리순으로 보여 줍니다(위치를 아직 켜지 않았으면 먼저 켭니다).
- **정보 카드**: 마커를 탭하면 말풍선 대신 지도 아래쪽 카드에 대표 사진·종류·번호·상태·주소·마지막 점검이 뜨고 **점검하기(권한 없으면 자세히)** 와 **길찾기**(카카오맵·네이버 지도 앱·구글 지도 중 선택) 버튼이 있습니다. 선택한 마커는 노란 테두리로 강조됩니다.
- 자동 검사: `scripts/map-view-browser-smoke.cjs`(묶음 합계·탭 확대, 라벨, 상태 칩·범례, 카드·길찾기 URL, 검색·Enter, 내 주변 거리순), `navigation-state-browser-smoke.cjs`(지도 보기와 필터 복원).

### 순찰 화면의 기록 밀집 방지

- 순찰 진행 중 **앞쪽 미점검**은 아직 표시하지 않은 등을 기본으로 보여 줍니다. 이미 직접 표시한 등은 후보 목록에서 숨기지만 저장한 기록은 그대로 유지합니다. 직전 등 상태를 정정하려면 **표시한 등 보기**를 눌러 다시 선택·표시할 수 있습니다. 현재 차 앞쪽에 해당 등만 있으면 안내 문구가 보이고, 필요할 때 다시 표시할 수 있습니다.
- 순찰 화면에는 **점검 기록 전체 수 · 확인 필요 수 · 정상 수와 가장 최근 1건**만 기본 표시합니다. 기록을 펼치면 최신 10건부터 보며 **전체 / 확인 필요(고장·점검필요·어두운 지점) / 정상**을 필터링하고 10건씩 더 불러올 수 있습니다. 이 목록의 **빼기**는 확인을 거쳐 해당 기록만 제외하며 데이터 저장 전 취소 기능과 혼동하지 않도록 합니다.
- 순찰 종료 후 결과 화면에서는 **고장·점검필요** 표시를 먼저 노출하고 **정상 점등 확인**은 접은 상태에서 건수로 표시합니다. 접으면 실제 순찰 기록이 삭제되거나 점검 상태가 바뀌지 않으며, 펼치면 모든 정상 기록을 다시 확인·정정할 수 있습니다.
- **GPS 근접 통과**는 계속 별도 수치이며 직접 관찰·정상 점등 확인의 건수에 합산하지 않습니다. 순찰 데이터 저장·내보내기·재개/복구와 역할 권한은 그대로 유지됩니다.
- 동승자가 조작하도록 기존 안전 안내·순찰 일시 정지 기능을 유지합니다. 모바일 세로·가로 모드에서 기록 목록을 펼쳐도 조작 버튼과 다음 시설 확인 기능이 화면 밖으로 사라지지 않도록 제한된 높이에서 스크롤됩니다.
- 지도 보기의 **따라가기**는 기본으로 **진행 방향이 위**가 되도록 지도를 돌립니다(차 표시는 항상 화면 위를 향하고, 번호·북쪽 표시는 바로 서 있음). 지도 왼쪽 위 **진행 방향 / 북쪽 위** 버튼으로 북쪽 고정 지도로 바꿀 수 있고 선택은 기기에 기억됩니다. 지도를 손으로 끌면 따라가기가 풀리면서 지도가 수평으로 돌아오고, **따라가기**를 다시 누르면 진행 방향 위로 복귀합니다. 차 표시는 지도 상자 높이와 무관하게 아래쪽 약 70% 지점에 두어 앞길이 넓게 보입니다.
- 지도 위 번호는 **앞쪽 미점검 카드의 번호와 같은 등**을 가리킵니다. 표시(고장·점검필요·정상)를 남긴 등은 카드 목록처럼 번호에서 빠지고 결과 색 원만 남으며, **표시한 등 보기**를 켜면 번호에 다시 포함됩니다. 선택한 등의 번호는 이웃 번호 위에 그려집니다.
- 기록을 펼치면 지도 크기는 유지한 채 측면 영역을 나눠 씁니다: 다음 등 카드 1장과 표시 버튼(한 줄로 축소)은 남고, 기록 목록이 나머지 공간에서 스크롤됩니다. 목록 높이는 `DGPatrolHistory.updatePanel`이 펼친 패널의 남은 높이를 재서 정하며(`<details>` 안은 flex로 늘일 수 없음) 화면 회전 시 다시 계산합니다. 가로 모드(높이 360~400px)에서는 화면을 격자로 나눠 **왼쪽에 지도(또는 카메라)와 그 아래 표시 버튼 한 줄**, **오른쪽에 미점검 목록과 접힌 기록(한 줄)**을 둡니다. 목록이 버튼 뒤에 가려지지 않고 2~3장이 보이며, 기록을 펼치면 오른쪽 열만 덮어 지도·번호·표시 버튼은 그대로 쓸 수 있습니다. 목록 보기(지도·카메라 끔)에서는 왼쪽 열을 표시 버튼 2×2가 채웁니다. 기준 동 안내 문장은 가로 모드에서 숨깁니다.
- 자동 검사: `scripts/tests/patrol-history.test.cjs`, `scripts/patrol-compact-browser-smoke.cjs`, `scripts/patrol-map-browser-smoke.cjs` (기존 Local browser workflows에 포함). 설치형 PWA와 야간 차량 현장 테스트는 별도로 진행해야 합니다.

## 철거된 등 숨기기

- 철거로 표시된 등(공공데이터 대장에서 빠진 가로등, 표찰에 '철거'가 붙은 보안등, 정보 수정에서 '철거된 등'을 고른 등)은 점검 목록·검색·지도·통계·순찰·밝기 검토에서 보이지 않아요. 지우지는 않아요.
- 예전 점검·사진·신고 이력과 표찰·QR 조회는 그대로 이 등을 찾아요(열면 '철거된 등으로 기록돼 있어요'가 보여요).
- 검색어가 철거된 등과 맞으면 목록 위에 「철거된 등 보기」가 나와요. 관리 현황 › 대장·등록 › **철거된 등**에서 전체 목록을 찾아볼 수 있어요.
- 잘못 표시된 등은 열어서 정보 수정에서 '철거된 등'을 해제하면 다시 목록에 나와요.

## 역할별 권한 (v46-roles-status)

- 관리 현황 아래 `내 역할: 점검자 · 담당 …`의 **할 수 있는 일**을 누르면 역할별 권한표가 나와요(내 열 강조). 관리자는 사용자·권한 화면 위에서도 같은 표를 볼 수 있어요.
- 권한이 없는 버튼을 누르면 필요한 역할과 내 역할을 함께 알려 줘요.
- 표의 기준은 화면의 `can()`과 서버 규칙(firestore.rules)이에요. 역할을 바꾸는 규칙이 달라지면 `index.html`의 `ROLE_CAPS`도 함께 고쳐요.
- 주민 신고 처리 상태 조회는 [주민 신고 운영 안내](citizen-report-plan.md#처리-상태-조회-v46)를 보세요.

## 체험 자료(seed) 버전 (v47-seed-safe)

- `seed/manifest.json`의 `version`을 올리면 체험 모드 기기가 새 체험 자료를 받아요. `purge:true`여도 **이 기기에서 사람이 남긴 기록(점검·신고·등록·등 상태)은 지우지 않아요.** 지난 체험 자료 중 아무도 고치지 않은 문서만 거둬들여요.
- 체험 자료는 같은 ID의 기존 기록을 덮어쓰지 않아요.
- 체험 모드는 기록이 기기마다 따로 남아요. 실제 운영은 Firebase 공유 모드(README "Firebase 적용")를 쓰세요.

## 등 상태의 순서 (v50-status-order)

- 등 상태를 정한 일의 시각을 `statusAt`에 남겨요(점검·순찰은 점검 시각, 수리 검수·관리자 변경은 그때 시각).
- 오프라인에서 남긴 점검이 늦게 전송돼도, 그 사이 수리 검수나 더 최근 점검이 있었다면 **상태는 바꾸지 않고** 마지막 점검일만 반영해요.
- 점검자는 점검·순찰 기록으로만 상태를 바꿔요. 등 화면의 "상태 바꾸기"(점검 기록 없이 상태만 변경)와 신고의 "고장으로 등록"은 관리자만 써요. 서버 규칙도 같아요.
- 기기 시계가 서버 시각보다 5분 넘게 앞선 점검 시각은 서버가 받지 않아요(시계를 맞춘 뒤 다시 보내면 돼요).
- 재점검 요청은 그 점검이 그 등의 최신 점검일 때만 등을 "점검필요"로 바꾸고, 고장·수리중이면 상태는 그대로 두고 요청만 남겨요(미점검 목록에 "재점검 요청"으로 떠요).
- 검수 대기 수는 검수 화면의 필터와 상관없이 세요. 최근 40건만 불러온 상태면 "40+"로 보이고, 오늘 할 일에서 누르면 전체를 불러와 "미확인만·전체 기간"으로 열어요.
- 반려됐거나 대장 등에 연결(대장반영)된 현장 등록은 사용 중인 등 수·목록·지도에서 빠지고 미등록 관리에는 남아요.

## 순찰·현장 화면 (v51-field-patrol)

- **끝내기:** "끝"이나 휴대폰 뒤로 가기를 누르면 먼저 물어요(달리는 중 실수로 끝나지 않게). 결과 화면의 **순찰 계속**으로 다시 돌아갈 수 있어요.
- **취소:** 마지막에 한 일(등 표시 또는 어두운 지점)을 순서대로 되돌려요. 같은 등을 다시 표시했다면 이전 표시로 돌아가요.
- **새 순찰:** 저장하지 않은 순찰이 있으면 "결과 보고 저장 / 이어서 순찰 / 버리고 새로 시작"을 물어요. 버리기 전에는 지우지 않아요.
- **이어서 저장:** 앞부분이 이미 저장 대기함에 들어간 순찰을 이어서 저장하면, 그 뒤에 추가한 표시·경로만 새 순찰 기록으로 저장해요(중복 점검 기록 없음).
- **아이콘:** 버튼 아이콘의 가운데를 눌러도 버튼이 눌려요.
- **내 주변 순:** 걸어가며 위치가 바뀌어도 검색칸이 다시 만들어지지 않아 입력이 끊기지 않아요. 위치 확인이 잠깐 늦어도(시간 초과) 꺼지지 않아요.
- **사진 캡션 좌표:** 그 점검에서 확인한 위치(또는 2분 이내의 주변 순 위치)만 넣어요.
- **표찰 스캔:** QR은 초당 약 7번만 읽고(가능하면 휴대폰 내장 인식기 사용), **주변 찾기**는 위치가 바뀔 때만 후보를 다시 계산해 저가형 휴대폰에서도 끊기지 않아요.
- **순찰 지도 회전:** 359°→1°처럼 북쪽을 지날 때 짧은 쪽으로 돌고, 가로 화면에서도 지도가 빈 곳 없이 채워져요.

## 기반 정리 (v52-foundation)

- **새 버전 설치:** 서비스 워커가 브라우저 캐시를 건너뛰고(`cache:'reload'`) 새 파일을 받아요. 몇 분 간격으로 버전이 바뀌어도 예전 화면·대장이 새 버전 이름으로 저장되지 않아요. 아이콘(svg)도 오프라인용으로 저장해요.
- **대장 교체:** 공공데이터 열(주소·지번·관리번호·위치 추정)을 비교·반영해요. 대장 교체로 들어온 등과 주소가 바뀐 등은 주소 표시를 다시 만들어요.
- **전송 재시도:** 신호가 약해 실패한 저장 대기 작업은 "연결됨" 신호가 없어도 15초부터 최대 5분 간격으로, 그리고 앱을 다시 볼 때 자동으로 다시 보내요.
- **정보 수정 이력:** 덮어쓰지 않고 덧붙여요(Firebase는 `arrayUnion`, 그 밖에는 최근 200건). 좌표 수정·철거 해제 때 함께 바뀐 위치 추정 표시·철거 일시도 되돌리기로 돌아와요.
- **검사:** 직원 앱 전역 이름이 두 번 선언되면 `check.mjs`가 실패해요. Node 22에서도 테스트가 모두 통과해요(Web Locks 대체). 실제 서비스 워커로 오프라인 재실행을 확인하는 스모크(`offline-reload-browser-smoke.cjs`)를 추가했어요.
- **CI:** 액션을 커밋 SHA로 고정하고(주석에 버전), 작업 시간 제한, Pages 배포는 진행 중에 끊지 않아요. Dependabot이 액션·functions 패키지 업데이트를 주마다 제안해요.

## 설정 파일을 바꿀 때는 버전도 올려요 (v53-shared-mode)

`firebase-config.js`·`report/config.js`·`app/map-config.js`도 오프라인용 앱 파일에 함께 저장돼요. 이 파일만 바꾸고 `sw.js`의 `VERSION`(과 `APP_VER`, `RELEASE_NOTES`)을 올리지 않으면, 이미 설치된 기기는 예전 설정을 계속 써요. 공유 모드 전환(v52 → v53)이 그 예예요.
